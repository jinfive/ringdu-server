
# Design

## 1. 목적

이 문서는 Ringdu 프로젝트의 제품과 인터페이스 설계 기준을 정의한다.

Ringdu는 학원, 선생님, 학부모, 학생을 연결하는 학원 관리 웹/앱 서비스다.  
초기에는 웹 MVP를 먼저 만들지만, 이후 실제 운영과 모바일 앱 확장까지 고려한다.

기능을 만들 때 단순히 동작하는 것에 그치지 않고, 사용자가 이해하기 쉽고 일관된 방식으로 사용할 수 있도록 설계 방향을 정리한다.

이 문서는 다음 내용을 다룬다.

- 제품 설계 원칙
- 사용자별 화면 설계 기준
- 인터페이스 설계 기준
- 상태, 에러, 빈 화면 처리 기준
- 권한별 화면 노출 기준
- 접근성 기준
- 반응형 설계 기준
- 디자인 리뷰 체크리스트
- 에이전트 작업 지침

---

## 2. 기본 설계 원칙

Ringdu의 제품과 인터페이스는 다음 원칙을 따른다.

- 사용자가 해야 할 일을 쉽게 이해할 수 있어야 한다.
- 중요한 정보와 행동이 먼저 보여야 한다.
- 화면 흐름은 예측 가능해야 한다.
- 같은 의미의 기능은 같은 방식으로 표현한다.
- 불필요한 선택지를 줄인다.
- 사용자의 실수를 줄이는 방향으로 설계한다.
- 에러가 발생했을 때 다음 행동을 안내한다.
- 사용자의 역할에 맞는 정보만 보여준다.
- 기능보다 사용자의 목적을 먼저 생각한다.
- 실제 학원 운영 흐름에 맞게 설계한다.

Ringdu는 여러 사용자 역할이 함께 쓰는 서비스이므로, 모든 화면은 “누가 이 화면을 사용하는가”를 먼저 기준으로 잡는다.

---

## 3. 사용자 역할 기준

Ringdu의 주요 사용자는 다음과 같다.

```txt
ADMIN
ACADEMY
TEACHER
PARENT
STUDENT
```

각 사용자는 목적이 다르므로 화면과 기능도 역할에 맞게 설계한다.

`OWNER`, `DESK`는 MVP 핵심 역할에서 제외한다. 초기에는 `ACADEMY` 계정이 원장, 데스크, 운영자 역할을 통합해서 담당한다.

### ADMIN

플랫폼 운영자다.

설계 기준:

- 전체 서비스 운영에 필요한 정보를 명확히 보여준다.
- 학원, 계정, 신고, 공지, 운영 설정 같은 관리 기능을 중심으로 설계한다.
- 일반 사용자 화면과 혼동되지 않게 한다.
- 위험한 운영 작업은 확인 단계를 둔다.

---

### ACADEMY

학원 계정이다.

설계 기준:

- 학원 전체 현황을 빠르게 파악할 수 있어야 한다.
- 선생, 학생, 부모-학생 연결, 클래스, 출석, 숙제, 공지, 청구서/수납 상태를 관리하기 쉽게 한다.
- 중요한 운영 지표와 해야 할 일을 우선 보여준다.
- 선생 등록/초대, 학생 등록, 학원 설정 같은 작업은 신중하게 설계한다.
- 상담 관리는 신규 학생 유입 CRM이 아니라 재원생 학생/학부모 상담 기록 관리로 설계한다.

---

### TEACHER

선생님이다.

설계 기준:

- 오늘 수업, 담당 학생, 출석, 숙제를 쉽게 확인할 수 있어야 한다.
- 수업 전후로 빠르게 처리해야 하는 작업을 중심으로 설계한다.
- 출석 체크, 숙제 확인, 학생 메모 등 반복 업무를 간단하게 만든다.
- 담당하지 않는 학생이나 수업 정보는 노출하지 않는다.

---

### PARENT

학부모다.

설계 기준:

- 자녀의 상태를 쉽게 확인할 수 있어야 한다.
- 출석, 시간표, 숙제, 청구서, 납부 상태를 명확하게 보여준다.
- 학원 내부 용어보다 학부모가 이해하기 쉬운 표현을 사용한다.
- 여러 자녀가 있는 경우 자녀 전환 흐름을 명확히 한다.
- 불안감을 주는 모호한 상태 표현을 피한다.

---

### STUDENT

학생이다.

설계 기준:

- 본인의 시간표, 출석, 숙제 정보를 쉽게 확인할 수 있어야 한다.
- 숙제 제출이나 확인 같은 행동은 단순해야 한다.
- 복잡한 관리 기능은 노출하지 않는다.
- 학생이 이해하기 쉬운 문구와 구조를 사용한다.

---

## 4. 제품 설계 기준

기능을 설계할 때는 다음을 확인한다.

- 이 기능이 실제 사용자 문제를 해결하는가
- 사용자가 이 기능을 왜 필요로 하는가
- 핵심 사용자는 누구인가
- 사용자는 어떤 상황에서 이 기능을 사용하는가
- 이 기능이 기존 흐름과 자연스럽게 연결되는가
- 기능이 너무 복잡하지 않은가
- 없어도 되는 기능을 추가하고 있지 않은가
- 사용자 역할별로 필요한 정보가 다른가
- 학원 운영 흐름과 맞는가
- 모바일에서도 사용할 가능성이 있는가

좋은 제품 설계는 기능이 많은 것이 아니라, 사용자가 필요한 일을 더 쉽게 끝낼 수 있게 하는 것이다.

---

## 5. 사용자 흐름

새 기능을 만들 때는 사용자 흐름을 먼저 정리한다.

기본 흐름:

```txt
사용자 목표
→ 진입 화면
→ 주요 행동
→ 확인 또는 결과
→ 다음 행동
```

확인할 것:

- 사용자가 어디서 이 기능을 시작하는가
- 첫 화면에서 무엇을 해야 하는지 알 수 있는가
- 중간에 막히는 지점은 없는가
- 완료 후 결과를 명확히 알 수 있는가
- 실패했을 때 다시 시도할 수 있는가
- 권한이 없는 사용자가 접근했을 때 어떻게 안내하는가
- 같은 기능을 다른 역할이 사용할 때 화면 차이가 필요한가

---

## 6. 화면 설계 원칙

화면은 정보를 명확하게 전달해야 한다.

원칙:

- 한 화면에는 하나의 주요 목적을 둔다.
- 가장 중요한 정보는 먼저 보여준다.
- 주요 버튼은 눈에 띄게 배치한다.
- 보조 행동은 주요 행동보다 덜 강조한다.
- 관련 있는 정보는 가까이 배치한다.
- 너무 많은 정보를 한 번에 보여주지 않는다.
- 긴 목록은 검색, 필터, 정렬, 페이지네이션을 고려한다.
- 반복되는 화면 구조는 일관되게 유지한다.
- 역할에 맞지 않는 기능은 화면에 노출하지 않는다.
- 권한이 필요한 기능은 백엔드 검증을 전제로 설계한다.

---

## 7. 회원가입 화면 설계 기준

Ringdu의 회원가입 화면은 권한 드롭다운 방식으로 만들지 않는다.

일반 회원가입 가능 유형:

```txt
선생님 가입
학부모 가입
학생 가입
```

화면 경로 기준:

```txt
/signup/teacher
/signup/parent
/signup/student
/signup/academy
```

설계 원칙:

- 사용자가 먼저 가입 유형을 선택하도록 한다.
- `ADMIN`은 회원가입 화면에 노출하지 않는다.
- `/signup/academy`는 즉시 로그인 가능한 일반 회원가입이 아니라 학원 가입 신청 화면이다.
- `OWNER`, `DESK`는 MVP 회원가입 유형으로 만들지 않는다.
- 학원 가입 신청은 학원명, 대표자명, 전화번호, 우편번호, 기본 주소, 상세 주소를 받는다.
- 주민등록번호는 어떤 회원가입 화면에서도 받지 않는다.
- 학원 계정은 신청 직후 승인 대기 상태이며 ADMIN 승인 후 로그인 가능하다.
- ADMIN 전용 학원 계정 직접 생성 화면은 운영 예외 기능으로 유지한다.
- 선생님은 가입 후 학원 연결 또는 승인 흐름으로 이어진다.
- 학부모는 가입 후 자녀 연결 흐름으로 이어진다.
- 학생은 가입 후 본인 정보 또는 학원 연결 흐름으로 이어진다.

간편가입 버튼:

```txt
카카오로 간편가입
네이버로 간편가입
구글로 간편가입
```

현재 실제 OAuth 연동 전이라면, 버튼 클릭 시 준비 중임을 안내한다.

예시:

```txt
간편가입은 준비 중입니다.
```

---

## 8. 인터페이스 구성 요소

버튼, 입력창, 목록, 카드, 모달 등 공통 UI 요소는 일관되게 사용한다.

Ringdu 프론트엔드는 Next.js, TypeScript, Tailwind CSS 기반으로 구성하며, shadcn/ui 스타일을 참고할 수 있다.

새로운 UI 패턴을 불필요하게 만들기보다 기존 화면 패턴을 재사용한다.

---

## 9. 버튼

버튼은 사용자의 행동을 명확히 표현해야 한다.

원칙:

- 버튼 문구는 행동을 명확히 표현한다.
- 주요 버튼과 보조 버튼을 구분한다.
- 위험한 행동은 명확하게 표시한다.
- 비활성화된 버튼은 이유를 알 수 있어야 한다.
- 제출 중에는 중복 클릭을 막는다.
- 권한이 없는 행동은 숨기거나 비활성화하되, 서버 검증도 반드시 필요하다.

좋은 예시:

```txt
저장하기
삭제하기
초대 보내기
출석 체크하기
숙제 등록하기
자녀 연결하기
청구서 확인하기
```

피해야 할 예시:

```txt
확인
완료
실행
처리
```

단, 문맥상 의미가 충분히 명확한 경우에는 짧은 버튼 문구를 사용할 수 있다.

---

## 10. 입력창

입력창은 사용자가 무엇을 입력해야 하는지 명확히 알려야 한다.

원칙:

- 입력해야 하는 값이 무엇인지 명확히 표시한다.
- 필요한 경우 예시를 제공한다.
- 필수 입력값과 선택 입력값을 구분한다.
- 잘못된 입력은 제출 후가 아니라 가능한 한 빠르게 안내한다.
- 입력 오류 메시지는 수정 방법을 알려야 한다.
- 개인정보 입력 항목은 꼭 필요한 경우에만 받는다.
- 비밀번호, 전화번호, 이메일 등은 형식 안내를 제공한다.

예시:

```txt
나쁨: 형식이 올바르지 않습니다.
좋음: 이메일 형식으로 입력해 주세요. 예: name@example.com
```

비밀번호 안내 예시:

```txt
영문, 숫자를 포함해 8자 이상 입력해 주세요.
```

---

## 11. 목록

목록은 많은 정보를 빠르게 확인하고 찾을 수 있어야 한다.

원칙:

- 목록의 각 항목은 구분이 명확해야 한다.
- 중요한 상태값을 쉽게 확인할 수 있어야 한다.
- 목록이 많아질 수 있으면 페이지네이션 또는 무한 스크롤을 고려한다.
- 검색과 필터가 필요한지 검토한다.
- 빈 목록일 때 안내 문구를 제공한다.
- 역할별로 필요한 목록 정보가 다르면 표시 항목을 다르게 설계한다.

Ringdu에서 목록이 많아질 수 있는 화면 예시:

```txt
학생 목록
선생님 목록
수업 목록
출석 목록
숙제 목록
청구서 목록
납부 내역
상담 내역
```

---

## 12. 카드

카드는 관련 정보를 묶어서 보여줄 때 사용한다.

원칙:

- 카드 하나에는 하나의 주제를 담는다.
- 핵심 정보와 보조 정보를 구분한다.
- 카드 안의 주요 행동은 명확히 배치한다.
- 카드가 너무 많은 정보를 담지 않도록 한다.
- 반복되는 카드 구조는 일관되게 유지한다.

예시:

```txt
오늘의 수업 카드
자녀 출석 상태 카드
미제출 숙제 카드
미납 청구서 카드
학원 공지 카드
```

---

## 13. 모달

모달은 사용자의 흐름을 강하게 막는 요소이므로 신중하게 사용한다.

원칙:

- 단순 안내는 모달보다 페이지 안 메시지나 토스트를 우선 고려한다.
- 삭제, 결제, 권한 변경, 계정 연결 해제처럼 중요한 확인이 필요한 경우 사용할 수 있다.
- 모달 안의 주요 행동과 취소 행동을 명확히 구분한다.
- 모달을 닫아도 입력 내용이 사라지는지 여부를 사용자가 예측할 수 있어야 한다.
- 모바일 화면에서 모달이 불편하지 않은지 확인한다.

---

## 14. 상태 설계

화면은 여러 상태를 고려해야 한다.

기본 상태:

- 기본 상태
- 로딩 상태
- 성공 상태
- 실패 상태
- 빈 상태
- 권한 없음 상태
- 비활성 상태
- 준비 중 상태

각 상태는 사용자가 현재 상황과 다음 행동을 이해할 수 있어야 한다.

---

## 15. 로딩 상태

로딩 상태는 사용자가 기다려야 하는 상황을 알려준다.

원칙:

- 데이터가 늦게 불러와질 수 있는 화면에는 로딩 상태를 제공한다.
- 긴 작업은 진행 중임을 명확히 보여준다.
- 사용자가 중복 클릭하지 않도록 처리한다.
- 로딩 중에도 가능한 경우 화면 구조를 유지한다.
- 목록 화면은 스켈레톤 UI를 고려한다.
- 제출 버튼은 제출 중 비활성화한다.

예시:

```txt
저장 중...
불러오는 중...
초대 전송 중...
출석 정보를 불러오는 중입니다.
```

---

## 16. 에러 상태

에러 상태는 원인과 다음 행동을 안내해야 한다.

원칙:

- 에러 메시지는 사용자 입장에서 이해할 수 있어야 한다.
- 내부 시스템 용어를 그대로 노출하지 않는다.
- 사용자가 할 수 있는 다음 행동을 안내한다.
- 재시도가 가능한 경우 재시도 버튼을 제공한다.
- 보안상 민감한 정보는 에러 메시지에 포함하지 않는다.
- 인증 실패와 권한 없음은 구분해서 안내한다.

예시:

```txt
나쁨: Internal Server Error
좋음: 일시적으로 요청을 처리하지 못했습니다. 잠시 후 다시 시도해 주세요.
```

로그인 에러 예시:

```txt
이메일 또는 비밀번호를 확인해 주세요.
```

권한 없음 예시:

```txt
이 화면에 접근할 권한이 없습니다.
```

---

## 17. 빈 상태

빈 상태는 단순히 비어 있음을 보여주는 것이 아니라 다음 행동을 안내해야 한다.

원칙:

- 왜 비어 있는지 설명한다.
- 사용자가 할 수 있는 다음 행동을 제공한다.
- 처음 사용하는 사용자를 돕는 문구를 제공한다.
- 필요하면 생성 버튼이나 안내 링크를 제공한다.
- 권한이 없어 생성할 수 없는 경우 생성 버튼을 보여주지 않는다.

예시:

```txt
아직 등록된 학생이 없습니다.
학생을 추가해 관리를 시작해 보세요.
```

```txt
아직 등록된 숙제가 없습니다.
수업에 필요한 숙제를 등록해 보세요.
```

```txt
아직 연결된 자녀가 없습니다.
자녀 연결을 요청해 주세요.
```

---

## 18. 성공 상태

사용자가 작업 완료를 명확히 알 수 있어야 한다.

원칙:

- 저장, 생성, 삭제, 전송 등 주요 행동 후 결과를 알려준다.
- 성공 메시지는 짧고 명확하게 작성한다.
- 완료 후 다음 행동이 필요하면 안내한다.
- 불필요하게 큰 알림은 피한다.
- 같은 작업에는 같은 성공 문구를 사용한다.

예시:

```txt
저장되었습니다.
초대가 전송되었습니다.
변경 사항이 반영되었습니다.
출석이 저장되었습니다.
숙제가 등록되었습니다.
자녀 연결 요청을 보냈습니다.
```

---

## 19. 권한 없음 상태

권한이 없는 화면이나 기능은 명확하게 처리한다.

원칙:

- 권한이 없는 기능은 가능한 한 노출하지 않는다.
- 직접 URL 접근 등으로 권한 없는 화면에 접근한 경우 안내한다.
- 권한 없음 메시지는 사용자를 비난하지 않는다.
- 필요한 경우 관리자나 학원 담당자에게 문의하도록 안내한다.
- 프론트에서 숨기는 것은 보안이 아니므로 백엔드 검증이 반드시 필요하다.

예시:

```txt
이 화면에 접근할 권한이 없습니다.
필요한 경우 학원 관리자에게 문의해 주세요.
```

---

## 20. 준비 중 상태

아직 구현되지 않았지만 화면에 임시로 노출되는 기능은 준비 중임을 명확히 안내한다.

원칙:

- 동작하지 않는 버튼을 아무 안내 없이 두지 않는다.
- 준비 중인 기능은 사용자에게 오해를 주지 않게 표시한다.
- 핵심 흐름을 방해하지 않도록 한다.
- 준비 중 기능이 너무 많으면 화면 신뢰도가 떨어질 수 있으므로 최소화한다.

예시:

```txt
간편가입은 준비 중입니다.
알림 기능은 준비 중입니다.
```

---

## 21. 위험한 행동

삭제, 권한 변경, 데이터 초기화, 결제 취소, 계정 연결 해제처럼 되돌리기 어려운 행동은 신중하게 설계한다.

원칙:

- 사용자가 행동의 결과를 이해할 수 있어야 한다.
- 필요한 경우 확인 단계를 둔다.
- 위험한 버튼은 일반 버튼과 시각적으로 구분한다.
- 되돌릴 수 없는 작업은 명확히 안내한다.
- 가능하면 복구 방법을 제공한다.
- 권한 변경은 대상 사용자와 변경 내용을 다시 확인하게 한다.

예시:

```txt
이 작업은 되돌릴 수 없습니다.
정말 삭제하시겠습니까?
```

```txt
이 사용자의 권한이 변경됩니다.
변경 후 접근 가능한 화면이 달라질 수 있습니다.
```

---

## 22. 문구 작성 기준

인터페이스 문구는 짧고 명확해야 한다.

원칙:

- 사용자가 이해하기 쉬운 표현을 사용한다.
- 내부 용어나 개발자 중심 표현을 피한다.
- 한 문장에 하나의 의미만 담는다.
- 명령형 문구는 부드럽고 직접적으로 작성한다.
- 에러 문구는 비난하지 않고 해결 방법을 안내한다.
- 학부모와 학생에게는 학원 내부 관리 용어를 과하게 노출하지 않는다.
- 같은 개념은 같은 이름으로 부른다.

좋은 문구:

```txt
비밀번호를 다시 입력해 주세요.
필수 항목을 입력해 주세요.
저장할 수 없습니다. 입력 내용을 확인해 주세요.
```

피해야 할 문구:

```txt
잘못된 요청입니다.
유효하지 않은 파라미터입니다.
사용자 오류입니다.
권한 객체가 없습니다.
```

---

## 23. 용어 기준

Ringdu 안에서 같은 개념은 같은 용어로 표현한다.

권장 용어:

```txt
학원
선생님
학부모
학생
자녀
수업
출석
숙제
청구서
납부 상태
초대
연결 요청
```

주의할 점:

- 같은 대상을 `회원`, `유저`, `사용자`로 섞어 쓰지 않는다.
- 학부모 화면에서는 `학생`보다 문맥에 따라 `자녀`를 우선 사용할 수 있다.
- 관리자 화면에서는 `사용자`를 사용할 수 있다.
- 개발 용어인 `role`, `provider`, `token`, `entity` 등은 일반 사용자 화면에 노출하지 않는다.

## 24. 일관성

제품 안의 표현과 동작은 일관되어야 한다.

확인할 것:

- 같은 기능은 같은 이름으로 부르는가
- 같은 상태는 같은 색상과 형태로 표현하는가
- 같은 행동은 같은 위치와 방식으로 제공하는가
- 버튼 문구와 알림 문구가 일관되는가
- 화면 전환 방식이 일관되는가
- 권한별 메뉴 구조가 일관되는가
- 리스트, 상세, 등록, 수정 화면 흐름이 일관되는가

일관성이 깨지면 사용자는 매번 새로 학습해야 한다.

---

## 25. 접근성

인터페이스는 가능한 많은 사용자가 사용할 수 있어야 한다.

원칙:

- 텍스트는 충분히 읽기 쉬워야 한다.
- 색상만으로 정보를 전달하지 않는다.
- 버튼과 링크는 구분 가능해야 한다.
- 클릭 가능한 영역은 충분히 커야 한다.
- 입력창에는 명확한 라벨을 제공한다.
- 키보드로 주요 기능을 사용할 수 있어야 한다.
- 이미지에는 필요한 경우 대체 텍스트를 제공한다.
- 에러 메시지는 입력창과 연결되어야 한다.
- 중요한 정보는 색상뿐 아니라 텍스트로도 표시한다.

예시:

```txt
출석 완료
결석
지각
미납
납부 완료
```

상태를 색상만으로 구분하지 않고 텍스트도 함께 제공한다.

---

## 26. 반응형 설계

화면은 다양한 기기 크기에서 사용할 수 있어야 한다.

원칙:

- 모바일, 태블릿, 데스크톱 화면을 고려한다.
- 작은 화면에서도 핵심 행동이 가능해야 한다.
- 긴 텍스트나 큰 표가 화면을 깨뜨리지 않도록 한다.
- 중요한 버튼이 화면 밖으로 밀려나지 않게 한다.
- 모바일에서는 입력과 터치 동작을 우선 고려한다.
- 표가 복잡하면 카드형 표시나 가로 스크롤을 고려한다.

Ringdu는 이후 모바일 앱 확장도 고려하므로, 웹 화면도 모바일 사용성을 무시하지 않는다.

---

## 27. 디자인 시스템

프로젝트에 디자인 시스템이 있다면 이를 우선한다.

확인할 것:

- 색상
- 타이포그래피
- 간격
- 버튼 스타일
- 입력창 스타일
- 카드 스타일
- 아이콘 사용 기준
- 상태 표시 기준
- 반응형 기준

디자인 시스템이 없다면 새로운 스타일을 계속 추가하지 말고, 기존 화면의 패턴을 재사용한다.

Tailwind CSS를 사용할 때도 임의의 스타일을 계속 늘리지 말고, 반복되는 패턴은 컴포넌트로 정리한다.

## 28. 프론트엔드 구현 기준

Ringdu 프론트엔드는 다음 기준을 따른다.

- Next.js App Router 구조를 사용한다.
- TypeScript를 사용한다.
- Tailwind CSS를 사용한다.
- React Hook Form과 Zod를 활용해 폼 검증을 관리한다.
- API 요청과 응답 타입을 명확히 관리한다.
- 백엔드 API 계약과 맞지 않는 임시 필드를 만들지 않는다.
- 권한별 화면 분기는 프론트에서 하되, 보안 검증은 백엔드가 담당한다.
- 소셜 로그인 UI는 실제 OAuth 연동 전까지 준비 중 상태로 처리한다.

- [ ] 이 기능의 주 사용자가 누구인지 명확한가?
- [ ] 사용자가 첫 화면에서 무엇을 해야 하는지 알 수 있는가?
- [ ] 주요 행동이 명확하게 보이는가?
- [ ] 불필요한 단계가 없는가?
- [ ] 실패했을 때 안내가 있는가?
- [ ] 빈 상태가 준비되어 있는가?
- [ ] 로딩 상태가 준비되어 있는가?
- [ ] 권한 없음 상태가 준비되어 있는가?
- [ ] 위험한 행동은 충분히 확인하는가?
- [ ] 문구가 사용자 입장에서 이해하기 쉬운가?
- [ ] 기존 화면과 일관성이 있는가?
- [ ] 모바일에서도 사용할 수 있는가?
- [ ] 접근성 문제가 없는가?
- [ ] 백엔드 권한 검증과 충돌하지 않는가?
- [ ] API 응답 구조와 맞는가?

## 30. 에이전트 작업 지침

AI 에이전트가 제품이나 인터페이스를 설계할 때는 다음을 따른다.

- 이 문서를 먼저 확인한다.
- 기존 화면과 문구 패턴을 우선한다.
- 새로운 UI 패턴을 불필요하게 만들지 않는다.
- 사용자의 주요 목표를 먼저 파악한다.
- 화면에는 하나의 핵심 목적을 둔다.
- 로딩, 에러, 빈 상태를 함께 고려한다.
- 권한 없음 상태를 함께 고려한다.
- 위험한 행동에는 확인 절차를 둔다.
- 내부 용어보다 사용자에게 익숙한 표현을 사용한다.
- 접근성과 반응형 동작을 고려한다.
- 설계가 커질 경우 별도 design-doc을 작성한다.
- 프론트 화면에서 숨겼다는 이유로 보안이 충족됐다고 판단하지 않는다.
- 백엔드 API 계약과 맞지 않는 임시 UI 구조를 만들지 않는다.

## 31. 핵심 원칙 요약

- 기능보다 사용자 목적을 먼저 본다.
- 역할별로 필요한 정보와 행동을 다르게 설계한다.
- 화면은 한 번에 이해할 수 있어야 한다.
- 중요한 행동은 명확하게 보여야 한다.
- 실패, 빈 상태, 권한 없음 상태도 설계의 일부다.
- 문구는 짧고 구체적으로 작성한다.
- 기존 패턴을 유지한다.
- 사용자의 실수를 줄이는 방향으로 설계한다.
- 일관성과 접근성을 지킨다.
- 실제 학원 운영 흐름과 맞게 설계한다.
- 프론트 화면 노출 제어와 백엔드 권한 검증을 구분한다.
