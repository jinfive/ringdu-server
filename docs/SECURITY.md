
# Security

## 1. 목적

이 문서는 Ringdu 프로젝트의 보안 기준을 정의한다.

Ringdu는 학원, 선생님, 학부모, 학생을 연결하는 학원 관리 웹/앱 서비스이며, 실제 배포와 운영까지 고려한다.  
따라서 인증, 권한, 사용자 데이터, 학원 데이터, 학생 데이터, 출석, 숙제, 청구, 납부 정보는 안전하게 다뤄야 한다.

이 문서는 다음 내용을 다룬다.

- 보안 모델
- 위협 가정
- 민감정보 처리 기준
- 인증 기준
- 인가 기준
- API 보안 기준
- 입력값 검증 기준
- 토큰과 쿠키 보안 기준
- 로그와 에러 처리 기준
- 시크릿 관리 기준
- 프론트엔드 보안 기준
- 배포 환경 보안 기준
- 보안 리뷰 체크리스트
- 에이전트 작업 지침

인증, 인가, 사용자 데이터, 토큰, 쿠키, 권한, API 접근, 민감한 설정을 변경하기 전에는 이 문서를 먼저 확인한다.

---

## 2. 보안 모델

Ringdu는 다음 보안 원칙을 따른다.

- 사용자는 허용된 데이터와 기능에만 접근할 수 있어야 한다.
- 인증은 사용자가 누구인지 확인하는 과정이다.
- 인가는 사용자가 무엇을 할 수 있는지 확인하는 과정이다.
- 권한 검증은 반드시 백엔드에서 수행한다.
- 프론트엔드에서 버튼을 숨기는 것은 보안이 아니다.
- 민감정보는 로그, API 응답, 에러 메시지, 클라이언트 코드에 노출되지 않아야 한다.
- 관리자 기능이나 권한이 필요한 작업은 명시적인 권한 검사를 거쳐야 한다.
- 외부 입력값은 신뢰하지 않고 검증해야 한다.
- 보안 로직은 단순하고 명확하며 테스트 가능해야 한다.

Ringdu에서 특히 보호해야 하는 데이터는 다음과 같다.

```txt
사용자 계정
비밀번호
Access Token
Refresh Token
학원 정보
학원 소속 관계
학생 정보
학부모-학생 연결 관계
출석 정보
숙제 정보
청구서와 납부 상태
운영자 기능
```

## 3. 권한 구조

Ringdu의 권한은 다음 6개다.

```txt
ADMIN
OWNER
DESK
TEACHER
PARENT
STUDENT
```

### ADMIN

Ringdu 플랫폼 관리자다.

보안 기준:

- 일반 회원가입으로 생성하지 않는다.
- 전체 학원과 서비스 운영 기능에 접근할 수 있다.
- OWNER 계정 생성 또는 부여 권한을 가질 수 있다.
- 운영자 기능은 별도 권한 검사를 거쳐야 한다.

---

### OWNER

학원 원장이다.

보안 기준:

- 일반 회원가입으로 생성하지 않는다.
- 자신이 소유하거나 관리하는 학원 데이터만 접근할 수 있어야 한다.
- 학원 구성원, 학생, 수업, 출석, 숙제, 청구, 납부 정보를 관리할 수 있다.
- 다른 학원의 데이터에 접근할 수 없어야 한다.

---

### DESK

학원 데스크, 실장, 상담, 수납 담당자다.

보안 기준:

- 일반 회원가입으로 생성하지 않는다.
- OWNER가 등록하거나 초대하는 방식으로 생성한다.
- 소속 학원의 운영 데이터만 접근할 수 있어야 한다.
- 권한 범위는 OWNER보다 제한될 수 있다.

---

### TEACHER

선생님이다.

보안 기준:

- 일반 회원가입이 가능하다.
- 가입 후 학원 연결 또는 승인 과정을 통해 학원에 소속된다.
- 담당 수업, 담당 학생, 출석, 숙제 범위 안에서만 접근할 수 있어야 한다.
- 담당하지 않는 학생이나 다른 학원의 데이터에 접근할 수 없어야 한다.

---

### PARENT

학부모다.

보안 기준:

- 일반 회원가입이 가능하다.
- 연결된 자녀의 정보만 조회할 수 있어야 한다.
- 자녀의 시간표, 출석, 숙제, 청구서, 납부 상태를 확인할 수 있다.
- 연결되지 않은 학생의 정보에 접근할 수 없어야 한다.

---

### STUDENT

학생이다.

보안 기준:

- 일반 회원가입이 가능하다.
- 본인 시간표, 출석, 숙제, 숙제 제출 정보만 접근할 수 있어야 한다.
- 다른 학생의 정보에 접근할 수 없어야 한다.

---

## 4. 회원가입 보안 기준

일반 회원가입 가능 권한:

```txt
TEACHER
PARENT
STUDENT
```

일반 회원가입 차단 권한:

```txt
ADMIN
OWNER
DESK
```

회원가입 보안 원칙:

- 회원가입 화면에 권한 드롭다운을 두지 않는다.
- `/signup/teacher`는 `TEACHER` 가입만 허용한다.
- `/signup/parent`는 `PARENT` 가입만 허용한다.
- `/signup/student`는 `STUDENT` 가입만 허용한다.
- `ADMIN`, `OWNER`, `DESK`는 프론트 화면에 노출하지 않는다.
- 서버에서도 `ADMIN`, `OWNER`, `DESK` 일반 회원가입을 차단한다.
- 클라이언트가 전달한 role 값을 그대로 신뢰하지 않는다.
- 학원명, 학원주소, 학원전화번호, 학원코드는 일반 회원가입에서 받지 않는다.

중요:

프론트엔드에서 권한 선택지를 숨기는 것만으로는 충분하지 않다.  
반드시 백엔드에서 허용된 가입 권한인지 검증해야 한다.

---

## 5. 위협 가정

다음과 같은 위협이 발생할 수 있다고 가정한다.

- 인증되지 않은 사용자가 보호된 API에 접근하려 할 수 있다.
- 인증된 사용자가 다른 사용자의 데이터에 접근하려 할 수 있다.
- 사용자가 자신의 권한을 넘어선 기능을 실행하려 할 수 있다.
- 다른 학원의 데이터에 접근하려는 요청이 발생할 수 있다.
- 학부모가 연결되지 않은 학생 정보를 조회하려 할 수 있다.
- 선생님이 담당하지 않는 학생이나 수업에 접근하려 할 수 있다.
- 클라이언트가 role, userId, academyId, studentId 값을 조작할 수 있다.
- 토큰, 쿠키, API Key가 탈취될 수 있다.
- 사용자 입력값에 악성 코드나 비정상 데이터가 포함될 수 있다.
- SQL Injection, XSS, CSRF, SSRF, 경로 조작, 명령어 삽입 공격이 발생할 수 있다.
- 무차별 로그인 시도나 크리덴셜 스터핑 공격이 발생할 수 있다.
- 민감정보가 로그, 에러 메시지, API 응답에 실수로 노출될 수 있다.
- 외부 라이브러리나 의존성에 보안 취약점이 있을 수 있다.
- 잘못된 환경 설정으로 내부 서비스나 시크릿이 노출될 수 있다.

## 6. 민감정보 처리

민감정보는 신중하게 다룬다.

민감정보의 예시는 다음과 같다.

- 비밀번호
- Access Token
- Refresh Token
- Cookie
- Session ID
- API Key
- 개인키
- JWT secret
- 이메일
- 전화번호
- 주소
- 학생 개인정보
- 학부모 개인정보
- 청구서와 납부 정보
- 내부 시스템 계정 정보
- 사용자 관련 비공개 기록

민감정보 처리 원칙:

- 비밀번호를 평문으로 저장하지 않는다.
- 비밀번호는 BCrypt로 암호화하여 저장한다.
- Access Token은 DB에 저장하지 않는다.
- Refresh Token 원문은 DB나 Redis에 저장하지 않는다.
- Refresh Token은 해시값만 저장한다.
- API 응답에 비밀번호, 토큰, 시크릿을 포함하지 않는다.
- 비밀번호, 토큰, API Key, 쿠키, Authorization Header를 로그에 남기지 않는다.
- 시크릿을 Git 저장소에 커밋하지 않는다.
- 운영 환경의 시크릿을 문서에 적지 않는다.
- 기능에 필요한 최소한의 사용자 데이터만 사용한다.
- Entity를 API 응답으로 직접 반환하지 않는다.

---

## 7. 인증

인증 로직은 신중하게 검토한다.

기본 원칙:

- 보호된 API는 인증을 요구해야 한다.
- 로그인 실패 응답은 계정 존재 여부를 과도하게 노출하지 않아야 한다.
- 비밀번호는 BCrypt로 검증한다.
- 세션이나 토큰의 만료 정책은 명확해야 한다.
- 로그아웃 시 Refresh Token 상태를 폐기해야 한다.
- 토큰 재발급 방식은 문서화하고 검토해야 한다.
- 인증 관련 에러 메시지는 사용자에게 필요한 수준으로만 제공한다.
- 공격자에게 유용한 정보를 주지 않는다.

다음 기능을 수정할 때는 반드시 인증 흐름을 확인한다.

```txt
회원가입
로그인
로그아웃
토큰 발급
토큰 재발급
Refresh Token Rotation
비밀번호 재설정
소셜 로그인
내 정보 조회
```

현재 방향:

- Access Token은 JWT로 발급한다.
- Access Token은 응답 body로 반환한다.
- 프론트엔드는 Access Token을 JavaScript 메모리에 저장한다.
- Refresh Token은 HttpOnly Cookie로 저장한다.
- Refresh Token 원문은 저장하지 않는다.
- Redis에는 Refresh Token 해시값만 저장한다.
- Refresh Token Rotation을 적용한다.

---

## 8. Access Token 보안 기준

Access Token은 사용자의 인증 상태를 증명하는 JWT다.

원칙:

- Access Token은 짧은 수명을 가진다.
- Access Token은 DB에 저장하지 않는다.
- Access Token은 Redis에 저장하지 않는다.
- Access Token을 로그에 남기지 않는다.
- Access Token에 불필요한 개인정보를 넣지 않는다.
- JWT secret은 코드에 하드코딩하지 않는다.
- JWT secret은 환경변수로 관리한다.
- 만료된 Access Token은 사용할 수 없어야 한다.

Access Token에 포함 가능한 정보는 최소화한다.

예시:

```txt
userId
role
issuedAt
expiresAt
```

주의:

- 이메일, 전화번호, 주소 등 개인정보를 토큰에 과도하게 넣지 않는다.
- 토큰 payload는 암호화가 아니라 인코딩된 값임을 전제로 설계한다.

---

## 9. Refresh Token 보안 기준

Refresh Token은 Access Token을 재발급하기 위한 민감한 값이다.

원칙:

- Refresh Token은 HttpOnly Cookie로 저장한다.
- JavaScript에서 Refresh Token에 접근할 수 없어야 한다.
- Refresh Token 원문은 DB에 저장하지 않는다.
- Refresh Token 원문은 Redis에 저장하지 않는다.
- Refresh Token은 SHA-256 등으로 해시한 tokenHash만 저장한다.
- 활성 Refresh Token은 Redis TTL로 만료를 관리한다.
- Refresh Token Rotation을 적용한다.
- refresh 요청마다 기존 Refresh Token을 폐기하고 새 Refresh Token을 발급한다.
- 사용된 Refresh Token은 `used-refresh:{oldTokenHash}`로 남은 만료 시간 또는 설정 TTL 동안 보관한다.
- 사용된 Refresh Token이 다시 들어오면 재사용 공격으로 보고 해당 사용자의 활성 Refresh Token을 정리한다.
- 로그아웃 시 Refresh Token을 폐기한다.
- Refresh Token 값, tokenHash, Authorization Header, Cookie 원문을 로그에 남기지 않는다.

Redis key 예시:

```txt
refresh:{tokenHash}
used-refresh:{oldTokenHash}
```

저장값은 현재 `userId`만 사용한다. Access Token은 Redis나 DB에 저장하지 않고 JWT 검증만 수행한다.

주의:

- Redis 장애 시 인증을 우회해서는 안 된다.
- Refresh Token이 유효하지 않으면 안전하게 재로그인을 요구한다.
- 재사용 감지 시 해당 사용자 세션 폐기를 고려한다.

---

## 10. Cookie 보안 기준

Refresh Token Cookie는 안전하게 설정한다.

기본 원칙:

- `HttpOnly: true`
- 운영 환경에서는 `Secure: true`
- `SameSite`는 운영 도메인 구조에 맞게 설정한다.
- Cookie Path는 필요한 범위로 제한한다.
- Refresh Token Cookie는 JavaScript에서 접근할 수 없어야 한다.

예상 방향:

```txt
Path: /api/auth
SameSite: Lax 또는 None
Secure: 운영 환경에서는 true
HttpOnly: true
```

주의:

- `SameSite=None`을 사용하는 경우 `Secure=true`가 필요하다.
- CORS 설정과 Cookie 설정은 함께 검토한다.
- 로컬 개발 환경과 운영 환경의 Cookie 설정을 구분한다.

---

## 11. 인가

인가는 반드시 서버에서 확인한다.

기본 원칙:

- 프론트엔드 검사만으로 권한을 판단하지 않는다.
- 보호된 작업은 사용자의 권한을 반드시 확인해야 한다.
- 사용자는 자신이 소유하지 않은 리소스를 조회하거나 수정할 수 없어야 한다.
- 다른 학원의 데이터에 접근할 수 없어야 한다.
- 관리자 또는 특수 권한 작업은 명시적인 권한 검사를 거쳐야 한다.
- 역할과 권한 로직은 가능한 한 중앙에서 관리한다.
- 권한 검사는 읽기 쉽고 테스트 가능해야 한다.

Ringdu에서 인가 검증이 필요한 대표 상황:

```txt
학원 정보 조회/수정
학원 구성원 관리
선생님 승인
데스크 직원 등록
학생 등록/수정
학부모-학생 연결
출석 등록/수정
숙제 등록/제출/검토
청구서 발행
납부 상태 변경
관리자 기능
```

권한 검증 예시:

- ADMIN만 플랫폼 운영 기능에 접근할 수 있다.
- OWNER는 자신이 관리하는 학원만 관리할 수 있다.
- DESK는 소속 학원의 운영 데이터만 접근할 수 있다.
- TEACHER는 담당 범위의 수업, 학생, 숙제, 출석만 접근할 수 있다.
- PARENT는 연결된 자녀의 데이터만 조회할 수 있다.
- STUDENT는 본인의 데이터만 조회하거나 제출할 수 있다.

## 12. API 보안

모든 API는 안전한 기본값을 가져야 한다.

API 보안 원칙:

- 요청 데이터를 검증한다.
- 예상하지 못한 입력값은 거부한다.
- 명시적인 Request DTO를 사용한다.
- 민감한 필드가 포함된 내부 객체를 그대로 응답하지 않는다.
- 클라이언트에 필요한 필드만 반환한다.
- Entity를 그대로 반환하지 않는다.
- 일관된 에러 응답 형식을 사용한다.
- 스택 트레이스나 내부 구현 정보를 사용자에게 노출하지 않는다.
- 민감한 엔드포인트에는 필요한 경우 요청 제한을 적용한다.
- 목록 조회 API에는 페이지네이션을 적용한다.
- 데이터를 반환하기 전에 소유권과 권한을 확인한다.

특히 다음 API는 보안 검토가 필요하다.

```txt
인증 API
사용자 프로필 API
학원 관리 API
학원 구성원 API
학생 관리 API
학부모-학생 연결 API
출석 API
숙제 API
청구와 납부 API
관리자 API
파일 업로드 API
파일 다운로드 API
비밀번호 재설정 API
토큰 재발급 API
```

## 13. 입력값 검증

외부 입력값은 신뢰하지 않는다.

외부 입력값의 예시:

- HTTP 요청 본문
- Query Parameter
- Path Parameter
- Header
- Cookie
- 업로드 파일
- Webhook 요청
- 외부 API 응답
- 환경 변수
- 사용자 작성 콘텐츠

입력값 검증 원칙:

- 타입, 길이, 형식, 허용 값을 검증한다.
- 가능하면 예상하지 못한 필드는 거부한다.
- 사용자 작성 콘텐츠를 화면에 표시할 때는 안전하게 처리한다.
- 원본 입력값을 SQL, Shell Command, 파일 경로, URL에 직접 연결하지 않는다.
- 파라미터 바인딩 또는 안전한 ORM 방식을 사용한다.
- 업로드 파일의 타입, 크기, 저장 위치를 검증한다.
- 클라이언트가 전달한 사용자 ID, 역할, 권한 값을 그대로 신뢰하지 않는다.
- 클라이언트가 전달한 academyId, studentId를 그대로 신뢰하지 않는다.
- 요청 사용자가 해당 리소스에 접근할 수 있는지 서버에서 확인한다.

회원가입 입력값 검증:

- 이메일 형식 확인
- 비밀번호 최소 기준 확인
- 이름 필수 여부 확인
- 전화번호 형식 확인
- 가입 가능한 role인지 확인
- 중복 이메일 확인

## 14. 시크릿 관리

시크릿은 소스 코드 밖에서 관리한다.

시크릿의 예시:

- 데이터베이스 비밀번호
- Redis 접속 정보
- API Key
- OAuth Client Secret
- 개인키
- JWT secret
- 암호화 키
- Webhook Secret
- 클라우드 접근 키

시크릿 관리 원칙:

- 시크릿을 Git에 커밋하지 않는다.
- 애플리케이션 코드에 시크릿을 하드코딩하지 않는다.
- 환경 변수 또는 안전한 시크릿 관리 도구를 사용한다.
- 노출이 의심되면 시크릿을 교체한다.
- 로컬, 테스트, 스테이징, 운영 환경의 시크릿을 분리한다.
- 운영 시크릿을 문서, 채팅, 이슈, 로그에 공유하지 않는다.
- `application.yml` 또는 `application.properties`에 운영 시크릿을 직접 작성하지 않는다.

로컬 개발용 값과 운영 시크릿은 구분한다.  
운영 기준에서는 DB password, JWT secret, Redis host, OAuth secret 등을 환경변수로 관리한다.

## 15. 로그와 에러 처리

로그는 문제 추적에 필요하지만, 민감정보를 노출할 수 있다.

로그 처리 원칙:

- 비밀번호를 로그에 남기지 않는다.
- Access Token을 로그에 남기지 않는다.
- Refresh Token을 로그에 남기지 않는다.
- Session Cookie를 로그에 남기지 않는다.
- API Key를 로그에 남기지 않는다.
- Authorization Header 전체를 로그에 남기지 않는다.
- 사용자에게 스택 트레이스를 노출하지 않는다.
- 에러 메시지에 내부 시스템 구조를 드러내지 않는다.
- 보안 관련 이벤트는 조사에 필요한 수준으로 기록한다.
- 민감한 요청 본문 전체를 로그에 남기지 않는다.

기록하면 좋은 보안 이벤트:

```txt
회원가입 실패
로그인 성공
로그인 실패
로그아웃
토큰 재발급 실패
Refresh Token 재사용 감지
권한 거부
관리자 작업
비밀번호 변경
비밀번호 재설정 요청
반복적이고 의심스러운 요청
```

로그에 포함할 수 있는 정보:

```txt
시간
이벤트 종류
사용자 ID
요청 출처
처리 결과
요청 경로
```

로그에 포함하면 안 되는 정보:

```txt
비밀번호
Access Token
Refresh Token
API Key
JWT secret
전체 개인정보
민감정보가 포함된 전체 요청 본문
```

## 16. 데이터 저장 보안

저장 데이터는 최소 노출 원칙을 따른다.

데이터 저장 원칙:

- 필요한 데이터만 저장한다.
- 적절한 제약조건과 인덱스를 사용한다.
- 개인정보를 보호한다.
- 필요한 경우 민감정보를 암호화한다.
- 비밀번호와 복구가 필요 없는 시크릿은 해시 처리한다.
- 민감정보의 불필요한 사본을 만들지 않는다.
- 데이터 보관과 삭제 기준을 정의한다.
- 삭제되거나 비활성화된 사용자가 보호된 리소스에 계속 접근하지 못하게 한다.

Ringdu 데이터 저장 원칙:

- User는 로그인 계정 정보만 담당한다.
- 학원 정보는 Academy로 분리한다.
- 학원 소속 관계는 AcademyMember로 분리한다.
- 학생 프로필은 Student로 분리한다.
- 학부모와 학생 관계는 StudentGuardian으로 분리한다.
- 학원과 학생 관계는 AcademyStudent로 분리한다.
- Refresh Token 원문은 DB에 저장하지 않는다.
- Access Token은 DB에 저장하지 않는다.

## 17. 파일 업로드 보안

파일 업로드 기능은 별도의 보안 검토가 필요하다.

파일 업로드 원칙:

- 파일 크기를 검증한다.
- 파일 타입을 검증한다.
- 파일 확장자만 신뢰하지 않는다.
- 업로드 파일을 실행 가능한 경로에 저장하지 않는다.
- 서버에서 안전한 파일명을 생성한다.
- 경로 조작 공격을 방지한다.
- 필요한 경우 파일 스캔을 수행한다.
- 비공개 파일은 접근 권한을 제한한다.
- 응답에 서버의 로컬 파일 경로를 노출하지 않는다.

Ringdu에서 파일 업로드가 사용될 수 있는 영역:

```txt
숙제 첨부파일
숙제 제출 파일
학원 공지 첨부파일
프로필 이미지
청구서 또는 영수증 파일
```

운영 환경에서는 S3 같은 외부 저장소 사용을 고려한다.

## 18. 외부 의존성 보안

외부 라이브러리는 보안 위험을 만들 수 있다.

의존성 관리 원칙:

- 필요한 경우에만 새 의존성을 추가한다.
- 유지보수가 잘 되는 라이브러리를 사용한다.
- 의존성을 주기적으로 업데이트한다.
- 중요한 패키지는 보안 권고를 확인한다.
- 사용하지 않는 의존성은 제거한다.
- 보안에 민감한 기능에는 방치된 라이브러리를 사용하지 않는다.
- Spring Boot, Spring Security, JWT, Redis 관련 의존성은 버전 호환성을 확인한다.

## 19. 외부 서비스 연동 보안

외부 서비스 연동은 보안 검토가 필요하다.

외부 서비스 예시:

```txt
카카오 OAuth
네이버 OAuth
구글 OAuth
이메일 발송
SMS 발송
푸시 알림
클라우드 스토리지
결제 서비스
Webhook 제공자
분석 도구
```

외부 서비스 연동 원칙:

- Webhook 서명을 검증한다.
- 내부 시크릿을 외부 서비스에 불필요하게 노출하지 않는다.
- 외부 연동에 부여하는 권한을 최소화한다.
- 외부 API 실패를 안전하게 처리한다.
- 외부에서 받은 데이터도 검증한 뒤 사용한다.
- OAuth provider에서 받은 사용자 정보도 그대로 신뢰하지 않는다.
- OAuth providerId는 provider와 함께 관리한다.

현재 실제 OAuth 연동 전에는 카카오, 네이버, 구글 버튼은 준비 중 상태로 처리한다.

## 20. 프론트엔드 보안

프론트엔드는 단독 보안 계층으로 신뢰하지 않는다.

프론트엔드 보안 원칙:

- 프론트엔드 코드에 민감한 시크릿을 저장하지 않는다.
- 비공개 API Key를 노출하지 않는다.
- 숨겨진 버튼이나 비활성화된 UI만으로 권한을 통제하지 않는다.
- 사용자 작성 콘텐츠는 안전하게 렌더링한다.
- 클라이언트에 불필요한 사용자 데이터를 보내지 않는다.
- 서버 측 권한 검사는 항상 필요하다.
- Access Token은 메모리에 저장한다.
- Refresh Token은 JavaScript에서 접근하지 못해야 한다.
- 권한별 화면 분기는 사용자 경험을 위한 것이며, 보안 검증은 백엔드가 담당한다.

회원가입 화면 보안 기준:

- 권한 드롭다운을 두지 않는다.
- `ADMIN`, `OWNER`, `DESK` 가입 버튼을 노출하지 않는다.
- 선생님, 학부모, 학생 가입 화면만 제공한다.
- 프론트가 보내는 role 값도 백엔드에서 다시 검증한다.

## 21. 환경과 배포 보안

배포 환경은 안전한 기본 설정을 사용해야 한다.

환경 및 배포 원칙:

- 운영 환경에서는 HTTPS를 사용한다.
- Cookie를 사용하는 경우 안전한 Cookie 설정을 적용한다.
- 운영 환경에서는 Refresh Token Cookie에 `Secure=true`를 적용한다.
- CORS는 신뢰할 수 있는 출처로 제한한다.
- 운영 환경에서는 디버그 모드를 비활성화한다.
- 내부 관리자 도구를 공개 인터넷에 노출하지 않는다.
- Health Check, Metrics, Debug Endpoint 접근을 제한한다.
- 서비스 계정과 접근 권한은 최소 권한 원칙을 따른다.
- 개발, 테스트, 스테이징, 운영 환경을 분리한다.
- 운영 DB, Redis, S3 접근 정보는 환경변수나 시크릿 관리 도구로 관리한다.

예상 운영 구성:

```txt
Backend: AWS EC2 또는 ECS
Database: AWS RDS PostgreSQL
Redis: AWS ElastiCache Redis
File Storage: S3
Frontend: Vercel 또는 S3 + CloudFront
Domain: ringdu.kr, api.ringdu.kr 등
```

## 22. CORS 보안

CORS는 필요한 출처만 허용한다.

원칙:

- 운영 환경에서는 모든 출처를 허용하지 않는다.
- 프론트엔드 운영 도메인만 허용한다.
- 로컬 개발 도메인과 운영 도메인을 구분한다.
- Cookie 인증이 필요한 경우 credentials 설정을 함께 검토한다.
- 허용 메서드와 헤더를 필요한 범위로 제한한다.
- 로컬 기본 허용 출처는 `http://localhost:3000`, `http://localhost:3001`, `http://localhost:3002`로 제한한다.

주의:

```txt
Access-Control-Allow-Origin: *
```

운영 환경에서 위와 같은 광범위한 설정은 피한다.

## 23. CSRF와 XSS 기준

Refresh Token을 Cookie로 사용하므로 CSRF와 XSS를 함께 고려한다.

### CSRF

원칙:

- Cookie 기반 인증 요청은 CSRF 위험을 검토한다.
- SameSite 설정을 적절히 사용한다.
- 중요한 상태 변경 API는 필요한 경우 CSRF 보호 또는 추가 검증을 고려한다.
- CORS 허용 출처를 제한한다.
- Refresh Token Cookie의 Path를 제한한다.

### XSS

원칙:

- 사용자 입력을 화면에 렌더링할 때 안전하게 처리한다.
- HTML을 직접 삽입하지 않는다.
- 외부에서 받은 콘텐츠를 신뢰하지 않는다.
- Access Token을 localStorage에 저장하지 않는다.
- Refresh Token은 JavaScript에서 접근할 수 없게 한다.

## 25. 보안 사고 대응 메모

보안 문제가 발견되면 다음 순서로 대응한다.

1. 가능한 경우 취약한 동작을 즉시 차단한다.
2. 영향을 받은 기능, 데이터, 사용자를 파악한다.
3. 노출된 시크릿이나 토큰이 있다면 교체한다.
4. 가장 작은 안전한 변경으로 문제를 수정한다.
5. 로그를 확인해 의심스러운 활동이 있었는지 조사한다.
6. 발생 원인과 수정 내용을 기록한다.
7. 같은 문제가 반복되지 않도록 테스트나 검증 절차를 추가한다.
8. 관련 문서를 갱신한다.
9. 남은 위험은 기술부채로 기록한다.

보안 문제를 숨기거나 무시하지 않는다.

## 26. 에이전트 작업 지침

AI 에이전트가 보안 관련 코드를 수정할 때는 다음을 따른다.

- 이 문서를 먼저 읽는다.
- 기존 보안 패턴을 우선한다.
- 명확한 이유 없이 새로운 인증 또는 인가 흐름을 만들지 않는다.
- 기존 권한 검사를 약화하지 않는다.
- 검증 로직을 제거하지 않는다.
- 민감한 필드를 API 응답에 추가하지 않는다.
- Entity를 API 응답으로 직접 반환하지 않는다.
- User에 학원 정보를 직접 넣지 않는다.
- 시크릿이나 토큰을 로그에 남기지 않는다.
- Refresh Token 원문을 저장하지 않는다.
- Access Token을 DB나 Redis에 저장하지 않는다.
- 위험한 변경은 구현 전에 실행 계획을 작성한다.
- 불확실하면 가장 작은 안전한 변경을 선택하고, 불확실한 부분을 문서에 기록한다.
- 문서와 코드가 다르면 현재 정상 동작하는 코드를 기준으로 판단한다.
- 임시 보안 예외를 만들었다면 기술부채로 기록한다.

## 28. 핵심 원칙 요약

- 보안은 프론트 화면 제어가 아니라 서버 검증에서 완성된다.
- 인증과 인가는 구분한다.
- 권한 검증은 반드시 백엔드에서 수행한다.
- `ADMIN`, `OWNER`, `DESK`는 일반 회원가입으로 생성하지 않는다.
- User는 로그인 계정 정보만 담당한다.
- 학원 정보는 Academy로 분리한다.
- 학원 소속 관계는 AcademyMember로 분리한다.
- 학부모와 학생 관계는 StudentGuardian으로 분리한다.
- Access Token은 DB에 저장하지 않는다.
- Refresh Token 원문은 저장하지 않는다.
- Refresh Token은 HttpOnly Cookie로 관리한다.
- Redis에는 Refresh Token 해시값만 저장한다.
- 비밀번호는 BCrypt로 암호화한다.
- Entity를 API 응답으로 직접 반환하지 않는다.
- 민감정보를 응답이나 로그에 노출하지 않는다.
- 운영 시크릿은 환경변수 또는 시크릿 관리 도구로 관리한다.
