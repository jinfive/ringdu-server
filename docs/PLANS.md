
# Plans

## 1. 목적

이 문서는 Ringdu 프로젝트의 계획, 로드맵, 현재 우선순위, 실행 중인 작업을 관리하기 위한 기준을 정의한다.

Ringdu는 학원, 선생님, 학부모, 학생을 연결하는 학원 관리 웹/앱 서비스이며, 실제 배포와 운영까지 고려한다.  
따라서 기능을 빠르게 추가하는 것뿐만 아니라, 작업 범위, 영향도, 검증 방법, 위험 요소를 명확히 관리해야 한다.

계획 문서는 단순한 할 일 목록이 아니다.  
다음 내용을 명확히 하기 위해 사용한다.

- 무엇을 만들 것인가
- 왜 필요한가
- 어떤 범위까지 작업할 것인가
- 어떤 순서로 진행할 것인가
- 어떤 위험이 있는가
- 어떤 검증이 필요한가
- 완료 기준은 무엇인가
- 남은 문제는 무엇인가

---

## 2. 계획 문서의 역할

계획 문서는 큰 작업을 시작하기 전에 방향과 범위를 정리하기 위해 사용한다.

다음 상황에서 사용한다.

- 새로운 핵심 기능을 추가할 때
- 기존 기능을 크게 수정할 때
- 아키텍처를 변경할 때
- 데이터베이스 구조를 변경할 때
- 인증, 인가, 보안 흐름을 변경할 때
- 외부 서비스를 연동할 때
- 큰 리팩토링을 진행할 때
- 기술부채를 정리할 때
- 배포 또는 운영 구조를 변경할 때
- 작업 우선순위를 정리할 때

작은 오타 수정, 단순 스타일 수정, 명확한 버그 수정처럼 범위가 작은 작업에는 별도 계획 문서가 필요하지 않을 수 있다.

단, 작은 작업이라도 보안, DB, 권한, 배포, 운영 안정성에 영향을 주면 계획을 작성한다.

## 3. 계획 관리 위치

계획 문서는 다음 위치에서 관리한다.

```txt
docs/exec-plans/
├── active/
├── completed/
└── tech-debt-tracker.md
```

### active

현재 진행 중이거나 앞으로 진행할 실행 계획을 둔다.

```txt
docs/exec-plans/active/
```

### completed

완료된 실행 계획을 둔다.

```txt
docs/exec-plans/completed/
```

### tech-debt-tracker.md

당장 해결하지 못한 기술부채를 기록한다.

```txt
docs/exec-plans/tech-debt-tracker.md
```

## 4. 계획이 필요한 작업 기준

다음 작업은 실행 전에 계획을 작성한다.

- 새로운 핵심 기능 추가
- API 구조 변경
- DB 테이블, 컬럼, 관계 변경
- 인증 또는 권한 흐름 변경
- 보안에 영향을 주는 변경
- 배포 방식 변경
- 외부 API 또는 외부 서비스 연동
- 공통 모듈 구조 변경
- 대규모 리팩토링
- 여러 파일과 계층에 영향을 주는 변경
- 실패 시 복구가 어려운 변경
- 운영 데이터에 영향을 줄 수 있는 변경
- 프론트와 백엔드 API 계약이 바뀌는 변경

Ringdu에서 특히 계획이 필요한 영역은 다음과 같다.

```txt
인증
권한
학원 관리
학생 관리
학부모-학생 연결
출석 관리
숙제 관리
청구와 납부
알림
파일 업로드
배포와 운영
```

## 5. 계획이 필요하지 않을 수 있는 작업

다음 작업은 별도 계획 없이 진행할 수 있다.

- 오타 수정
- 문서 표현 개선
- 작은 UI 문구 수정
- 단순한 변수명 정리
- 명확한 버그 수정
- 기존 패턴을 그대로 따르는 작은 기능 추가
- 테스트 코드 일부 보완
- 코드 포맷 정리

단, 작은 작업이라도 다음 항목에 영향을 주면 계획을 작성한다.

- 보안
- 인증
- 권한
- 데이터베이스
- 배포
- 운영 안정성
- 사용자 개인정보
- 프론트와 백엔드 API 계약

## 7. 로드맵 작성 기준

로드맵은 장기적인 작업 방향을 정리할 때 사용한다.

로드맵은 다음 기준으로 작성한다.

- 현재 가장 중요한 문제를 먼저 다룬다.
- 핵심 기능과 안정성을 우선한다.
- 있으면 좋은 기능보다 반드시 필요한 기능을 먼저 한다.
- 큰 작업은 여러 단계로 나눈다.
- 각 단계의 완료 기준을 명확히 한다.
- 보안, 안정성, 품질 개선을 기능 개발과 함께 고려한다.
- 실제 운영에 필요한 작업을 뒤로 미루지 않는다.
- 웹 MVP 이후 모바일 앱 확장 가능성을 고려한다.

## 9. 우선순위 기준

작업 우선순위는 다음 기준으로 판단한다.

| 기준 | 설명 |
|---|---|
| 사용자 영향 | 사용자에게 직접 영향을 주는가 |
| 안정성 영향 | 장애나 데이터 오류를 줄이는가 |
| 보안 영향 | 보안 위험을 줄이는가 |
| 핵심 기능 여부 | 프로젝트의 핵심 흐름에 필요한가 |
| 작업 차단 여부 | 다른 작업을 진행하기 위해 먼저 필요한가 |
| 구현 난이도 | 지금 진행 가능한 수준인가 |
| 유지보수 효과 | 이후 개발을 더 쉽게 만드는가 |
| 운영 영향 | 실제 배포와 운영에 영향을 주는가 |

Ringdu에서는 다음 영역에 영향을 주는 작업을 우선적으로 본다.

- 사용자 계정
- 로그인과 인증
- 권한 검증
- 학원 소속 관계
- 학부모와 학생 연결
- 출석 데이터
- 청구와 납부 데이터
- 운영 보안
- 배포 안정성

---

## 10. 우선순위 분류

작업은 다음과 같이 분류한다.

### P0

즉시 처리해야 하는 작업이다.

예시:

- 서비스 장애
- 보안 취약점
- 데이터 손상 가능성
- 로그인 불가
- 핵심 기능 중단
- 다른 학원 데이터에 접근 가능한 권한 문제
- 비밀번호나 토큰 노출 위험

---

### P1

빠르게 처리해야 하는 중요한 작업이다.

예시:

- 핵심 기능 구현
- 중요한 버그 수정
- 권한 문제 수정
- 배포 전 필수 작업
- 인증 흐름 구축
- API 계약 정리
- 주요 테스트 보완

---

### P2

일정 안에서 처리하면 좋은 작업이다.

예시:

- 기능 개선
- 성능 개선
- 테스트 보완
- 문서 정리
- 반복 코드 정리
- 사용성 개선

---

### P3

당장 급하지 않은 작업이다.

예시:

- 코드 정리
- 작은 편의 기능
- 낮은 우선순위의 리팩토링
- 추후 검토 사항
- 디자인 디테일 개선

## 11. 현재 우선순위 작성 형식

현재 우선순위는 다음 형식으로 작성한다.

```md
# Current Priorities

## P0

- 

## P1

- 

## P2

- 

## P3

- 
```

주의:

- 현재 우선순위는 너무 길게 작성하지 않는다.
- 실제로 진행할 수 있는 작업 중심으로 적는다.
- 이미 완료된 작업은 남겨두지 않는다.
- 로드맵과 기술부채를 섞지 않는다.

---

## 12. 진행 상태 기준

작업 상태는 다음 기준으로 관리한다.

| 상태 | 의미 |
|---|---|
| Proposed | 제안됨 |
| Planned | 계획됨 |
| In Progress | 진행 중 |
| Blocked | 막힘 |
| Done | 완료 |
| Deferred | 보류 |
| Cancelled | 취소 |

상태는 실제 진행 상황에 맞게 갱신한다.  
완료되지 않은 작업을 `Done`으로 표시하지 않는다.

---

## 13. 작업 기록 기준

각 작업에는 다음 정보를 기록한다.

- 작업명
- 상태
- 우선순위
- 담당자 또는 작업 주체
- 관련 문서
- 관련 파일
- 시작일
- 완료일
- 검증 방법
- 남은 문제

예시:

```md
## 작업명

- 상태:
- 우선순위:
- 담당자:
- 관련 문서:
- 관련 파일:
- 시작일:
- 완료일:
- 검증 방법:
- 남은 문제:
```

작업 기록은 의사결정과 변경 이력을 남기기 위한 용도다.  
불필요하게 세세한 작업 로그를 모두 적을 필요는 없다.

---

## 14. 기술부채 관리

기술부채는 숨기지 않고 기록한다.

기술부채로 기록해야 하는 경우:

- 임시 구현이 들어간 경우
- 테스트 없이 기능을 먼저 구현한 경우
- 중복 코드가 많지만 즉시 정리하지 못한 경우
- 구조 개선이 필요하지만 범위가 큰 경우
- 성능 문제가 예상되지만 당장 장애는 아닌 경우
- 문서가 부족하거나 실제 코드와 다른 경우
- 추후 리팩토링이 필요한 경우
- 보안상 개선이 필요한 경우
- 운영상 위험이 있는 경우

기술부채는 다음 문서에 기록한다.

```txt
docs/exec-plans/tech-debt-tracker.md
```

기록할 때는 다음 내용을 포함한다.

- 문제
- 영향
- 우선순위
- 관련 영역
- 해결 방향
- 완료 기준

모든 미구현 기능을 기술부채로 기록하지 않는다.  
정상적인 제품 로드맵과 기술부채를 구분한다.

---

## 15. 완료된 계획 처리

작업이 완료되면 다음을 수행한다.

1. 실행 계획의 완료 기준을 확인한다.
2. 검증 결과를 기록한다.
3. 남은 문제가 있으면 기술부채에 기록한다.
4. 관련 문서를 갱신한다.
5. 계획 문서를 `active`에서 `completed`로 이동한다.

완료된 계획은 삭제하지 않는다.  
나중에 의사결정 근거와 변경 이력을 확인하기 위해 보관한다.

---

## 16. 계획 작성 시 주의사항

계획은 너무 복잡하게 작성하지 않는다.

좋은 계획은 다음 조건을 만족한다.

- 목표가 명확하다.
- 작업 범위가 분명하다.
- 하지 않을 일이 적혀 있다.
- 구현 순서가 현실적이다.
- 위험 요소가 드러나 있다.
- 검증 방법이 있다.
- 완료 기준이 확인 가능하다.
- 관련 문서와 파일이 연결되어 있다.

좋지 않은 계획:

- 목표가 모호하다.
- 작업 범위가 계속 커진다.
- 한 번에 너무 많은 것을 바꾸려 한다.
- 검증 방법이 없다.
- 실패했을 때 되돌릴 방법이 없다.
- 설계 문서와 실행 계획이 뒤섞여 있다.
- 단순 할 일 목록만 있고 완료 기준이 없다.

---

## 17. 설계 문서와 실행 계획의 차이

설계 문서와 실행 계획은 역할이 다르다.

| 구분 | 역할 |
|---|---|
| 설계 문서 | 어떤 구조로 만들지, 왜 그렇게 할지 설명 |
| 실행 계획 | 어떤 순서로 구현하고 어떻게 검증할지 설명 |
| 기술부채 문서 | 남아 있는 문제와 위험을 추적 |
| 제품 스펙 문서 | 사용자가 무엇을 필요로 하는지 정의 |

예시:

```txt
docs/design-docs/auth-design.md
→ 인증 구조와 토큰 흐름 설계

docs/exec-plans/active/implement-auth.md
→ 인증 기능 구현 순서와 검증 계획

docs/exec-plans/tech-debt-tracker.md
→ 인증 구현 중 남은 기술부채 기록
```

실행 계획에는 구조 설명만 길게 적지 않는다.  
구조와 선택 이유는 설계 문서에 남기고, 실행 계획에는 작업 순서와 검증 기준을 남긴다.

---

## 18. 브랜치와 작업 흐름 연결

실행 계획은 실제 작업 흐름과 연결된다.

기본 작업 흐름은 다음 문서를 따른다.

```txt
docs/WORKFLOW.md
```

원칙:

- 작업 전 현재 브랜치와 작업 디렉터리를 확인한다.
- develop을 기준으로 작업 브랜치를 만든다.
- 작업 전 이슈를 생성한다.
- 작업 후 테스트 또는 수동 검증을 수행한다.
- PR 대상은 develop으로 한다.
- 후속 조치가 필요하면 관련 계획이나 기술부채에 기록한다.

실행 계획은 Git 작업을 대신하지 않는다.  
실제 브랜치 전략과 PR 규칙은 `docs/WORKFLOW.md`를 따른다.

---

## 19. 에이전트 작업 지침

AI 에이전트가 작업할 때는 다음을 따른다.

- 큰 작업은 먼저 실행 계획을 작성한다.
- 기존 계획이 있으면 그 계획을 우선 확인한다.
- 계획 없이 대규모 구조 변경을 하지 않는다.
- 작업 범위를 임의로 확장하지 않는다.
- 보안, DB, 아키텍처 변경은 별도 계획을 둔다.
- 진행 중 발견한 기술부채는 기록한다.
- 완료된 작업은 검증 방법과 결과를 남긴다.
- 계획과 실제 구현이 달라지면 계획 문서를 갱신한다.
- 문서와 코드가 다르면 현재 정상 동작하는 코드를 기준으로 판단한다.
- 특정 기능을 구현하면서 관련 문서가 오래되었으면 함께 갱신한다.
- 임시 해결을 넣었다면 기술부채로 남긴다.

## 20. 계획 리뷰 체크리스트

실행 계획을 시작하기 전에 다음을 확인한다.

- [ ] 목표가 명확한가?
- [ ] 작업 범위가 명확한가?
- [ ] 하지 않을 작업이 정리되어 있는가?
- [ ] 관련 문서와 파일이 적혀 있는가?
- [ ] 구현 순서가 현실적인가?
- [ ] 보안 영향이 있는가?
- [ ] 안정성 영향이 있는가?
- [ ] DB 변경이 있는가?
- [ ] API 변경이 있는가?
- [ ] 프론트엔드 영향이 있는가?
- [ ] 운영 환경 영향이 있는가?
- [ ] 검증 방법이 있는가?
- [ ] 롤백 방법이 있는가?
- [ ] 기술부채가 생길 가능성이 있는가?
- [ ] 관련 문서를 갱신해야 하는가?

## 22. 핵심 원칙 요약

- 계획은 작업을 느리게 하기 위한 문서가 아니다.
- 계획은 작업 범위와 완료 기준을 명확히 하기 위한 도구다.
- 큰 변경은 계획 없이 진행하지 않는다.
- 완료 기준이 없는 작업은 완료된 것이 아니다.
- 정상적인 미구현 기능과 기술부채를 구분한다.
- 기술부채는 숨기지 않고 기록한다.
- 설계 문서와 실행 계획의 역할을 구분한다.
- 계획은 실제 구현에 맞게 계속 갱신한다.
- Ringdu는 실제 운영을 고려하므로 보안, 권한, 데이터 정합성, 배포 안정성을 계획 단계에서 함께 본다.
