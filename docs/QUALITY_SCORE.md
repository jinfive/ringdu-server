
# Quality Score

## 1. 목적

이 문서는 Ringdu 프로젝트의 품질 평가 기준을 정의한다.

Ringdu는 학원, 선생님, 학부모, 학생을 연결하는 학원 관리 웹/앱 서비스이며, 실제 배포와 운영까지 고려한다.  
따라서 코드는 단순히 동작하는 것만으로 충분하지 않다.

변경 사항은 다음 관점에서 평가한다.

- 요구사항을 정확히 반영했는가
- 기존 기능을 깨지 않는가
- 코드 구조가 유지보수 가능한가
- 인증과 권한이 안전하게 처리되는가
- 데이터 정합성을 지키는가
- 프론트엔드와 백엔드 API 계약이 명확한가
- 테스트 또는 검증 방법이 있는가
- 필요한 문서가 갱신되었는가
- 운영 환경에서 문제가 될 위험이 없는가

이 문서는 코드 리뷰, 문서 리뷰, 설계 검토, 에이전트 작업 결과 검토에 사용한다.

---

## 2. 품질 평가 원칙

좋은 변경은 다음 조건을 만족해야 한다.

- 기존 기능을 깨지 않는다.
- 변경 범위가 명확하다.
- 코드가 읽기 쉽다.
- 책임이 적절히 분리되어 있다.
- 테스트 또는 검증 방법이 있다.
- 보안과 안정성을 해치지 않는다.
- 필요한 문서가 갱신되어 있다.
- 불필요한 복잡성을 만들지 않는다.
- Ringdu의 도메인 구조와 맞다.
- 운영 환경에서 문제가 될 수 있는 부분을 고려한다.

Ringdu에서는 특히 다음 항목을 중요하게 본다.

- 사용자 계정과 학원 정보의 분리
- 학원 소속 관계 관리
- 학부모와 학생 연결 관계
- 역할별 권한 검증
- Entity 직접 응답 방지
- 민감정보 노출 방지
- 인증 토큰 안전성
- 테스트 가능성

## 3. 점수 기준

품질 점수는 1점부터 5점까지 사용한다.

| 점수 | 의미 |
|---|---|
| 5 | 매우 좋음. 바로 유지보수 가능한 수준 |
| 4 | 좋음. 사소한 개선만 필요 |
| 3 | 보통. 동작은 하지만 개선 필요 |
| 2 | 낮음. 구조, 안정성, 테스트 등에 명확한 문제 있음 |
| 1 | 매우 낮음. 재작업 또는 큰 수정 필요 |

점수는 단순 평균만 보지 않는다.  
보안, 권한, 데이터 정합성 문제가 있으면 평균이 높아도 승인하지 않을 수 있다.

| 도메인 적합성 | Ringdu의 도메인 구조와 맞는가 |
| 안정성 | 실패 상황을 고려했는가 |
| 보안성 | 민감정보와 권한 처리가 안전한가 |
| 데이터 정합성 | 테이블 관계와 상태 변경이 안전한가 |
| 테스트 가능성 | 테스트하거나 검증하기 쉬운가 |
| 문서화 | 필요한 설명과 변경 이력이 남아 있는가 |
| 일관성 | 기존 프로젝트 패턴을 따르는가 |
| 단순성 | 불필요한 복잡성을 피했는가 |
| 운영 가능성 | 실제 배포와 운영 환경을 고려했는가 |

## 5. 세부 평가 기준

## 5.1 정확성

확인할 것:

- 요구사항을 충족하는가
- 예외 상황을 처리하는가
- 잘못된 입력에 대해 안전하게 동작하는가
- 기존 기능을 깨지 않는가
- 예상한 결과를 반환하는가
- 프론트엔드가 기대하는 API 응답과 일치하는가

점수 기준:

| 점수 | 기준 |
|---|---|
| 5 | 요구사항과 예외 상황을 모두 잘 처리함 |
| 4 | 요구사항은 충족하며 사소한 보완만 필요 |
| 3 | 기본 동작은 하지만 일부 예외 처리가 부족함 |
| 2 | 요구사항 일부가 누락되었거나 동작이 불안정함 |
| 1 | 핵심 기능이 제대로 동작하지 않음 |

---

## 5.2 가독성

확인할 것:

- 이름이 명확한가
- 코드 흐름이 이해하기 쉬운가
- 메서드와 함수가 과도하게 길지 않은가
- 주석 없이도 의도가 드러나는가
- 불필요하게 복잡한 표현을 피했는가
- 도메인 용어가 일관되게 사용되는가

점수 기준:

| 점수 | 기준 |
|---|---|
| 5 | 코드를 쉽게 읽고 의도를 이해할 수 있음 |
| 4 | 대체로 읽기 쉽고 일부 정리만 필요 |
| 3 | 이해는 가능하지만 구조나 이름 개선 필요 |
| 2 | 흐름을 이해하기 어렵고 정리가 필요 |
| 1 | 유지보수가 어려울 정도로 복잡함 |

---

## 5.3 유지보수성

확인할 것:

- 변경 범위가 작고 명확한가
- 중복이 과도하지 않은가
- 도메인 책임이 잘 분리되어 있는가
- 향후 기능 추가 시 수정 범위가 예측 가능한가
- 특정 구현에 과하게 묶여 있지 않은가
- 임시 구현이 숨어 있지 않은가

점수 기준:

| 점수 | 기준 |
|---|---|
| 5 | 변경과 확장이 쉽고 책임이 명확함 |
| 4 | 유지보수에 큰 문제 없음 |
| 3 | 동작은 하지만 일부 구조 개선 필요 |
| 2 | 변경 시 영향 범위가 크고 예측이 어려움 |
| 1 | 작은 변경도 큰 수정이 필요한 구조 |

---

## 5.4 책임 분리

확인할 것:

- Controller에 비즈니스 로직이 없는가
- Service가 핵심 흐름을 담당하는가
- Repository가 데이터 접근에 집중하는가
- Entity가 외부 응답에 직접 노출되지 않는가
- DTO가 요청과 응답을 적절히 분리하는가
- global/common 영역이 남용되지 않는가

점수 기준:

| 점수 | 기준 |
|---|---|
| 5 | 계층과 모듈 책임이 명확함 |
| 4 | 대부분 책임이 잘 분리되어 있음 |
| 3 | 일부 계층에 책임이 섞여 있음 |
| 2 | 여러 책임이 한 곳에 몰려 있음 |
| 1 | 구조적 분리가 거의 없음 |

---

## 5.5 도메인 적합성

Ringdu의 도메인 구조와 맞는지 평가한다.

확인할 것:

- User가 로그인 계정 정보만 담당하는가
- 학원 정보가 Academy로 분리되어 있는가
- 학원 소속 관계가 AcademyMember로 분리되어 있는가
- 학생 프로필이 Student로 분리되어 있는가
- 학부모와 학생 관계가 StudentGuardian으로 분리되어 있는가
- 학원과 학생 관계가 AcademyStudent로 분리되어 있는가
- 권한별 책임이 혼동되지 않는가

잘못된 예:

```txt
users 테이블에 academyName, academyAddress, academyPhone, academyCode를 넣는 것
```

점수 기준:

| 점수 | 기준 |
|---|---|
| 5 | Ringdu 도메인 구조와 잘 맞고 확장 가능함 |
| 4 | 대체로 도메인 분리가 적절함 |
| 3 | 동작은 하지만 일부 책임이 섞여 있음 |
| 2 | 도메인 관계가 불명확해 향후 수정 위험이 큼 |
| 1 | 핵심 도메인 구조와 맞지 않음 |

---

## 5.6 안정성

확인할 것:

- 실패 상황을 고려했는가
- 트랜잭션 경계가 적절한가
- 중복 요청이나 재시도 상황을 고려했는가
- 장애 발생 시 원인을 추적할 수 있는가
- 외부 서비스 실패를 처리할 수 있는가
- 데이터 상태가 중간에 깨질 위험이 없는가

점수 기준:

| 점수 | 기준 |
|---|---|
| 5 | 실패 상황과 복구 가능성이 충분히 고려됨 |
| 4 | 주요 실패 상황을 처리함 |
| 3 | 기본 처리는 있으나 일부 위험이 남아 있음 |
| 2 | 실패 상황 처리가 부족함 |
| 1 | 장애나 데이터 손상 가능성이 큼 |

---

## 5.7 보안성

확인할 것:

- 인증이 필요한 기능에 인증이 적용되어 있는가
- 권한 검사가 서버에서 이루어지는가
- 사용자가 다른 사용자의 데이터에 접근할 수 없는가
- 다른 학원 데이터에 접근할 수 없는가
- 학부모가 연결되지 않은 학생 정보를 볼 수 없는가
- 선생님이 담당하지 않는 학생이나 수업에 접근할 수 없는가
- 민감정보가 응답이나 로그에 노출되지 않는가
- 입력값 검증이 적절한가
- 비밀번호가 BCrypt로 암호화되는가
- Refresh Token 원문이 저장되지 않는가
- JWT secret이 코드에 하드코딩되지 않는가

점수 기준:

| 점수 | 기준 |
|---|---|
| 5 | 보안 위험이 잘 통제되어 있음 |
| 4 | 주요 보안 기준을 충족함 |
| 3 | 기본 보안은 있으나 일부 보완 필요 |
| 2 | 명확한 보안 취약 가능성이 있음 |
| 1 | 민감정보 노출 또는 권한 우회 위험이 큼 |

보안성 점수가 2점 이하이면 전체 변경은 재검토한다.

---

## 5.8 데이터 정합성

확인할 것:

- 외래키 관계가 적절한가
- unique 제약조건이 필요한 곳에 있는가
- 상태값 enum이 명확한가
- 삭제, 비활성화, 탈퇴 정책이 데이터 관계를 깨지 않는가
- 학원과 사용자 관계가 중복되지 않는가
- 학부모와 학생 관계가 중복되지 않는가
- 출석, 숙제, 청구 같은 상태 변경 데이터가 일관되게 관리되는가

점수 기준:

| 점수 | 기준 |
|---|---|
| 5 | 데이터 관계와 상태 변경이 안정적으로 설계됨 |
| 4 | 주요 정합성 기준을 충족함 |
| 3 | 기본 구조는 있으나 일부 제약조건 보완 필요 |
| 2 | 중복, 누락, 잘못된 관계 가능성이 있음 |
| 1 | 데이터 손상 또는 심각한 정합성 문제가 발생할 수 있음 |

## 5.9 테스트 가능성

확인할 것:

- 핵심 로직을 테스트할 수 있는가
- 테스트 대상이 과도하게 외부 환경에 의존하지 않는가
- 주요 성공/실패 케이스를 검증했는가
- 버그 수정 시 재발 방지 테스트가 있는가
- 수동 검증 방법이라도 명확한가
- 권한별 접근 테스트가 가능한가
- 프론트와 백엔드 API 계약을 검증할 수 있는가

점수 기준:

| 점수 | 기준 |
|---|---|
| 5 | 자동 테스트와 검증 방법이 충분함 |
| 4 | 핵심 테스트가 있고 일부 보완만 필요 |
| 3 | 테스트는 부족하지만 수동 검증 가능 |
| 2 | 검증 방법이 불명확함 |
| 1 | 테스트하거나 검증하기 어려움 |

## 5.10 문서화

확인할 것:

- 변경 이유가 기록되어 있는가
- 사용 방법 또는 동작 방식이 설명되어 있는가

- 실행 계획 또는 기술부채가 필요한 경우 기록되었는가

점수 기준:

| 점수 | 기준 |

| 5 | 필요한 문서가 명확하고 최신 상태임 |

| 2 | 중요한 설명이 누락됨 |
| 1 | 문서가 없거나 잘못된 정보를 제공함 |

## 5.13 운영 가능성

확인할 것:

- 운영 시크릿이 코드에 하드코딩되지 않았는가
- 환경변수로 설정 가능한가
- 로컬, 테스트, 운영 환경이 구분되는가
- 로그에 문제 추적에 필요한 정보가 남는가
- 로그에 민감정보가 남지 않는가
- 배포 후 장애 발생 시 원인 파악이 가능한가
- 운영 DB 데이터에 위험한 변경이 없는가
- Docker, PostgreSQL, Redis 설정이 운영 기준과 충돌하지 않는가

점수 기준:

| 점수 | 기준 |
|---|---|
| 5 | 실제 운영 환경까지 충분히 고려됨 |
| 4 | 운영에 큰 문제 없음 |
| 3 | 기본 운영은 가능하지만 일부 보완 필요 |
| 2 | 운영 시 위험 요소가 명확히 있음 |
| 1 | 운영 적용이 어려운 수준 |

## 8. 개선 메모 작성 기준

개선 메모는 구체적으로 작성한다.

좋지 않은 예:

```txt
코드가 별로다.
```

좋은 예:

```txt
AuthService에 회원가입, 로그인, 토큰 재발급 책임이 모두 들어 있어 메서드가 길어지고 있다.
토큰 관련 로직은 별도 컴포넌트로 분리하는 것을 검토한다.
```

개선 메모에는 다음을 포함한다.

- 문제가 있는 위치
- 왜 문제가 되는지
- 어떤 방향으로 개선할지
- 바로 수정할지, 기술부채로 남길지
- 관련 문서를 갱신해야 하는지

## 9. 기술부채 기록 기준

다음 경우에는 기술부채로 기록한다.

- 지금 당장 수정하기에는 범위가 큰 문제
- 동작은 하지만 구조 개선이 필요한 문제
- 성능이나 안정성 위험이 있지만 즉시 장애는 아닌 문제
- 테스트가 부족하지만 단기적으로 배포가 필요한 경우
- 임시 구현이 들어간 경우
- 문서와 실제 코드가 불일치하는 경우
- 보안이나 운영상 개선이 필요한 경우

기술부채 기록 위치:

```txt
docs/exec-plans/tech-debt-tracker.md
```

기록할 때는 다음 내용을 포함한다.

- 문제
- 영향
- 우선순위
- 관련 영역
- 해결 방향
- 완료 기준

정상적인 미구현 기능은 기술부채로 보지 않는다.  
예정된 기능과 기술부채를 구분한다.

## 11. 에이전트 작업 지침

AI 에이전트가 코드를 작성하거나 수정할 때는 다음을 따른다.

- 이 문서를 품질 평가 기준으로 사용한다.
- 기존 코드와 문서의 패턴을 우선한다.
- 동작만 맞추는 것이 아니라 유지보수성을 고려한다.
- 복잡한 변경은 작게 나누어 진행한다.
- 보안과 안정성을 해치는 변경을 하지 않는다.
- 권한 검증을 프론트 화면 노출 제어로 대체하지 않는다.
- Entity를 API 응답으로 직접 반환하지 않는다.
- User에 학원 정보를 직접 넣지 않는다.
- 테스트 또는 검증 방법을 함께 제시한다.
- 개선이 필요하지만 즉시 수정하지 못하는 부분은 기술부채로 기록한다.
- 품질 점수가 낮은 변경은 재검토한다.
- 문서와 코드가 다르면 현재 정상 동작하는 코드를 기준으로 판단한다.

## 13. 핵심 원칙 요약

- 품질은 동작 여부만으로 판단하지 않는다.
- Ringdu는 실제 운영을 고려하므로 보안, 권한, 데이터 정합성을 중요하게 본다.
- User는 계정 정보만 담당해야 한다.
- 학원, 학생, 학부모 관계는 별도 도메인으로 분리한다.
- Controller, Service, Repository 책임을 분리한다.
- Entity를 API 응답으로 직접 반환하지 않는다.
- 민감정보를 응답이나 로그에 노출하지 않는다.
- 테스트 또는 검증 방법이 있어야 한다.
- 필요한 문서는 변경과 함께 갱신한다.
- 품질이 낮은 변경은 기술부채로 남기거나 재검토한다.
