
# Design Docs

## 1. 목적

이 디렉터리는 Ringdu 프로젝트의 상세 설계 문서를 관리한다.

Ringdu는 학원, 선생님, 학부모, 학생을 연결하는 학원 관리 웹/앱 서비스이며, 실제 배포와 운영까지 고려한다.  
따라서 핵심 기능을 구현하기 전에 구조, 흐름, 책임, 데이터, 권한, 예외 상황, 위험 요소를 정리해야 한다.

설계 문서는 다음 내용을 관리한다.

- 기능별 설계 방향
- 주요 의사결정 기록
- 아키텍처 변경 근거
- 데이터 흐름
- API 흐름
- 인증과 권한 흐름
- 보안 고려사항
- 운영상 위험 요소
- 구현 전 검토 사항

설계 문서는 단순 작업 지시서가 아니다.  
왜 이런 구조를 선택했는지 남기는 기록이다.

---

## 2. 문서 역할

설계 문서는 기능을 구현하기 전에 방향을 정리하기 위해 사용한다.

다음 상황에서는 설계 문서 작성을 권장한다.

- 새로운 핵심 기능을 추가할 때
- 기존 기능의 구조를 크게 변경할 때
- 여러 도메인이 함께 변경될 때
- 데이터베이스 구조가 바뀔 때
- 인증 또는 권한 흐름이 바뀔 때
- 사용자 역할별 접근 범위가 달라질 때
- 외부 서비스를 연동할 때
- 캐시, 배치, 비동기 작업을 추가할 때
- 장애나 성능에 영향을 줄 수 있는 구조를 변경할 때
- 구현 전에 선택지를 비교해야 할 때

Ringdu는 `ADMIN`, `OWNER`, `DESK`, `TEACHER`, `PARENT`, `STUDENT` 권한이 분리되어 있으므로, 권한이나 접근 제어가 포함된 기능은 설계 단계에서 반드시 검토한다.

## 5. 설계 문서가 필요한 작업

다음 작업은 설계 문서를 작성하는 것이 좋다.

* 인증 방식 변경
* 권한 구조 변경
* 학원, 선생님, 학부모, 학생 관계 변경
* 학생과 학부모 연결 구조 변경
* 학원과 학생 소속 구조 변경
* 출석 관리 기능 추가
* 숙제 관리 기능 추가
* 청구서, 납부, 수납 기능 추가
* 알림, 이메일, 문자, 푸시 기능 추가
* 파일 업로드 또는 다운로드 기능 추가
* 외부 API 연동
* 소셜 로그인 연동
* Redis, 캐시, 세션 저장소 적용
* 배치 또는 비동기 작업 추가
* 검색, 필터, 정렬 구조 변경
* 대규모 리팩토링
* 장애 대응 구조 변경
* 운영 배포 구조 변경

특히 다음 영역은 설계 문서를 우선 작성한다.

```txt

권한

결제 또는 납부

파일 처리
알림
```

## 6. 설계 문서가 필요하지 않을 수 있는 작업

다음 작업은 별도 설계 문서 없이 진행할 수 있다.

* 오타 수정
* 간단한 문구 수정
* 작은 스타일 수정
* 단순한 버그 수정
* 기존 패턴을 그대로 따르는 작은 기능 추가
* 테스트 케이스 일부 보완
* 문서 내용 보완
* 코드 포맷 정리

단, 작은 작업이라도 다음에 영향을 주면 설계 문서를 작성하거나 기존 설계 문서를 갱신한다.

* 보안
* 인증
* 권한
* 데이터베이스
* 배포
* 운영 안정성
* 사용자 개인정보
* 프론트와 백엔드 API 계약

## 7. 설계 원칙

Ringdu 설계는 다음 원칙을 따른다.

* 단순한 구조를 우선한다.
* 기존 프로젝트 패턴을 우선한다.
* 도메인별 책임을 명확히 분리한다.
* 변경 범위를 작게 유지한다.
* 보안과 안정성을 함께 고려한다.
* 데이터 흐름을 명확히 한다.
* 실패 상황을 설계에 포함한다.
* 구현보다 유지보수를 먼저 생각한다.
* 불필요한 추상화를 피한다.
* 운영 환경에서 문제가 될 수 있는 부분을 미리 검토한다.
* 선택한 이유와 포기한 대안을 기록한다.

Ringdu는 실제 운영을 고려하므로, 빠르게 만드는 것보다 안정적으로 유지할 수 있는 구조를 우선한다.

## 8. 도메인 설계 기준

Ringdu는 사용자 계정과 학원 정보를 분리한다.

기본 원칙:

* `User`는 로그인 계정 정보만 담당한다.
* 학원 정보는 `Academy`가 담당한다.
* 학원과 운영 인력의 관계는 `AcademyMember`가 담당한다.
* 학생 프로필은 `Student`가 담당한다.
* 학부모와 학생 관계는 `StudentGuardian`이 담당한다.
* 학원과 학생 관계는 `AcademyStudent`가 담당한다.

잘못된 방향:

```txt
users 테이블에 academyName, academyAddress, academyPhone, academyCode를 넣는 것
```

올바른 방향:

```txt
users
→ 로그인 계정 정보

academies
→ 학원 정보

academy_members
→ 학원과 OWNER / DESK / TEACHER의 소속 관계

students
→ 학생 프로필

student_guardians
→ 학부모와 학생 관계

academy_students
→ 학원과 학생 관계
```

설계 문서에서는 이 분리 원칙을 기준으로 도메인 책임을 판단한다.

## 9. 권한과 보안 설계 기준

Ringdu의 권한은 다음 6개다.

```txt
ADMIN
OWNER
DESK
TEACHER
PARENT
STUDENT
```

일반 회원가입 가능 권한:

```txt
TEACHER
PARENT
STUDENT
```

일반 회원가입 차단 권한:

```txt
ADMIN
OWNER
DESK
```

권한 설계 시 확인할 내용:

* 이 API를 호출할 수 있는 권한은 무엇인가?
* 사용자가 본인 데이터만 접근해야 하는가?
* 학원 소속 관계를 확인해야 하는가?
* 학부모가 연결된 자녀 데이터만 볼 수 있는가?
* 선생님이 담당 학생 또는 담당 수업만 관리해야 하는가?
* OWNER와 DESK의 권한 범위가 다른가?
* ADMIN만 수행해야 하는 작업인가?

보안 설계 시 확인할 내용:

* 비밀번호나 토큰이 응답에 포함되지 않는가?
* Entity를 직접 응답하지 않는가?
* 민감정보가 로그에 남지 않는가?
* 운영 시크릿이 코드에 하드코딩되지 않는가?
* 권한 검증이 프론트가 아니라 백엔드에서 수행되는가?
* Refresh Token 원문이 저장되지 않는가?
* 운영 환경에서 HTTPS와 Secure Cookie를 고려했는가?

## 10. 설계 결정 기록

중요한 설계 결정은 문서에 남긴다.

기록할 내용:

* 어떤 결정을 했는가
* 왜 그 결정을 했는가
* 어떤 대안을 검토했는가
* 선택하지 않은 대안은 왜 제외했는가
* 이 결정이 어떤 영향을 주는가

예시:

```md
## 결정: User에는 학원 정보를 넣지 않는다.

### 이유

사용자 계정과 학원 정보는 책임이 다르다.
한 사용자가 여러 학원과 연결될 수 있고, OWNER / DESK / TEACHER 관계도 학원별로 달라질 수 있다.

### 검토한 대안

- users 테이블에 학원 정보를 직접 저장
- users와 academies를 분리하고 관계 테이블 사용

### 선택

users와 academies를 분리하고, academy_members로 소속 관계를 관리한다.

### 영향

학원 관련 기능을 구현할 때는 User가 아니라 Academy와 AcademyMember를 기준으로 설계해야 한다.
```

## 11. 대안 비교 기준

설계 대안을 비교할 때는 다음 기준을 사용한다.

| 기준     | 설명                      |
| ------ | ----------------------- |
| 단순성    | 구현과 이해가 쉬운가             |
| 유지보수성  | 나중에 수정하기 쉬운가            |
| 안정성    | 실패 상황을 잘 견디는가           |
| 보안성    | 권한, 인증, 민감정보를 안전하게 다루는가 |
| 확장성    | 기능이 커져도 구조가 유지되는가       |
| 성능     | 필요한 성능을 만족하는가           |
| 일관성    | 기존 구조와 잘 맞는가            |
| 검증 가능성 | 테스트하거나 확인하기 쉬운가         |
| 운영 가능성 | 실제 배포 후 관리하기 쉬운가        |

가장 복잡한 구조가 좋은 설계는 아니다.
현재 단계에서 필요한 만큼 단순하게 만들되, 운영 중 문제가 될 수 있는 부분은 미리 막는다.

## 13. 설계 문서와 실행 계획의 차이

설계 문서와 실행 계획은 역할이 다르다.

| 구분    | 역할                       |
| ----- | ------------------------ |
| 설계 문서 | 어떤 구조로 만들지, 왜 그렇게 할지 설명  |
| 실행 계획 | 어떤 순서로 구현할지, 어떻게 검증할지 설명 |

예시:

```txt
docs/design-docs/auth-design.md
→ 인증 구조와 토큰 흐름 설계

docs/exec-plans/active/implement-auth.md
→ 인증 기능 구현 순서와 작업 계획
```

설계 문서는 방향을 정하고, 실행 계획은 실제 작업 순서를 정한다.

설계 문서에는 브랜치명, 커밋 메시지, 작업 순서를 과도하게 넣지 않는다.
그런 내용은 실행 계획 문서에서 관리한다.

| 작업 흐름    | `docs/WORKFLOW.md`                     |

설계와 구현이 달라지면 관련 문서도 함께 갱신한다.

## 15. 설계 문서 상태

설계 문서는 다음 상태를 사용할 수 있다.

| 상태           | 의미           |
| ------------ | ------------ |
| Draft        | 초안           |
| Proposed     | 제안됨          |
| Approved     | 승인됨          |
| Implementing | 구현 중         |
| Implemented  | 구현 완료        |
| Deprecated   | 더 이상 사용하지 않음 |

문서 상단에 상태를 표시할 수 있다.

예시:

```md
# Auth Design

- 상태: Draft
- 작성일: YYYY-MM-DD
- 마지막 수정일: YYYY-MM-DD
```

상태는 문서 관리용이다.
실제 구현 상태와 다르면 문서를 갱신한다.

---

## 16. 에이전트 작업 지침

AI 에이전트가 설계 관련 작업을 할 때는 다음을 따른다.

* 이 색인 문서를 먼저 확인한다.
* 관련 설계 문서가 있는지 확인한다.
* 설계 문서가 있으면 그 내용을 우선한다.
* 설계 문서가 없고 변경 범위가 크면 새 설계 문서를 작성한다.
* 기존 코드와 문서가 다르면 현재 동작하는 코드를 기준으로 판단한다.
* 보안, DB, 권한, 배포에 영향을 주는 설계는 관련 문서도 함께 확인한다.
* 설계와 구현이 달라지면 설계 문서를 갱신한다.
* 설계를 임의로 확장하지 않는다.
* 복잡한 설계는 대안과 선택 이유를 함께 기록한다.
* 특정 기능의 구현 순서는 실행 계획 문서에 작성한다.
* 설계 문서에는 구조와 결정 이유를 중심으로 남긴다.

## 17. 핵심 원칙 요약

* 설계 문서는 구현 전에 방향을 정리하는 문서다.
* 모든 작업에 설계 문서가 필요한 것은 아니다.
* 구조, DB, 보안, 권한, 외부 연동 변경에는 설계 문서를 작성하는 것이 좋다.
* Ringdu는 사용자 계정, 학원, 학생, 학부모 관계를 분리해서 설계한다.
* 권한 검증은 반드시 백엔드에서 수행한다.
* 설계 문서는 선택 이유와 대안을 남겨야 한다.
* 실행 계획은 설계 이후에 작성한다.
* 설계와 실제 구현이 달라지면 문서를 갱신한다.
