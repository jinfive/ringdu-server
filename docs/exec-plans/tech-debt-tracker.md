
# Tech Debt Tracker

## 1. 목적

이 문서는 Ringdu 프로젝트에서 발견된 기술부채를 추적하기 위한 문서이다.

기술부채는 당장 기능 동작에는 문제가 없더라도, 장기적으로 유지보수성, 안정성, 보안, 성능, 확장성, 운영 가능성에 악영향을 줄 수 있는 문제를 의미한다.

Ringdu는 학원, 선생님, 학부모, 학생을 연결하는 학원 관리 웹/앱 서비스이며, 실제 배포와 운영까지 고려한다.  
따라서 기술부채는 단순 코드 정리 대상이 아니라, 운영 안정성과 사용자 신뢰를 지키기 위해 관리해야 하는 항목이다.

이 문서는 다음 내용을 관리한다.

- 알려진 기술부채
- 영향도
- 우선순위
- 담당자
- 현재 상태
- 관련 영역
- 해결 방향
- 완료 기준
- 해결 이력

---

## 2. 기술부채 기록 기준

다음에 해당하는 항목은 기술부채로 기록한다.

- 임시 구현이 들어간 경우
- 중복 코드가 많지만 즉시 정리하지 못한 경우
- 테스트가 부족한 경우
- 문서가 부족하거나 오래된 경우
- 문서와 실제 코드가 불일치하는 경우
- 구조 개선이 필요하지만 범위가 큰 경우
- 성능 문제가 예상되는 경우
- 보안상 개선이 필요한 경우
- 장애 가능성이 있지만 당장 해결하지 못한 경우
- 오래된 라이브러리나 의존성을 사용하는 경우
- 설정, 배포, 운영 방식에 위험이 있는 경우
- 데이터베이스 구조 개선이 필요한 경우
- 인증이나 권한 검증이 불완전한 경우
- 민감정보 처리 방식에 개선이 필요한 경우
- 프론트와 백엔드 API 계약이 불명확한 경우

기술부채는 숨기지 않는다.  
당장 해결하지 못하더라도 문제, 영향, 해결 방향을 남긴다.

---

## 3. 기술부채로 보지 않는 항목

다음은 기술부채가 아니라 일반 작업 계획 또는 제품 로드맵으로 관리한다.

- 아직 구현하지 않은 신규 기능
- MVP 이후로 미뤄둔 기능
- 기획상 나중에 추가하기로 한 기능
- 현재 범위에 포함되지 않은 외부 연동
- 아직 시작하지 않은 화면 개발
- 별도 이슈로 계획된 정상적인 개발 작업

예시:

```txt
로그인 기능이 아직 없음
→ 다음 개발 작업 또는 로드맵

Redis Refresh Token Rotation이 아직 구현되지 않음
→ 인증 기능 구현 범위

출석 관리 기능이 아직 없음
→ 제품 기능 로드맵

카카오, 네이버, 구글 OAuth 실제 연동이 아직 없음
→ 추후 소셜 로그인 기능
````

단, 임시로 구현한 구조가 나중에 보안, 안정성, 유지보수성에 문제를 만들 수 있다면 기술부채로 기록한다.

---

## 4. 상태 기준

| 상태          | 의미                   |
| ----------- | -------------------- |
| Open        | 아직 해결되지 않음           |
| In Progress | 해결 중                 |
| Blocked     | 외부 요인이나 선행 작업 때문에 막힘 |
| Deferred    | 의도적으로 보류             |
| Resolved    | 해결 완료                |
| Won't Fix   | 해결하지 않기로 결정          |

상태는 현재 상황에 맞게 갱신한다.
해결된 항목은 삭제하지 않고 `Resolved` 상태로 남긴다.

---

## 5. 우선순위 기준

| 우선순위 | 의미         | 예시                            |
| ---- | ---------- | ----------------------------- |
| P0   | 즉시 해결 필요   | 보안 취약점, 데이터 손상 가능성, 서비스 장애 위험 |
| P1   | 빠르게 해결 필요  | 핵심 기능에 영향을 주는 구조 문제, 주요 성능 문제 |
| P2   | 일정 내 해결 권장 | 유지보수성 저하, 테스트 부족, 중복 코드       |
| P3   | 낮은 우선순위    | 문서 보완, 작은 리팩토링, 코드 스타일 정리     |

우선순위는 고정값이 아니다.
프로젝트 단계, 배포 여부, 사용자 영향도에 따라 다시 조정할 수 있다.

---

## 6. 영향도 기준

| 영향도    | 의미                                 |
| ------ | ---------------------------------- |
| High   | 서비스 안정성, 보안, 데이터 정합성, 핵심 기능에 직접 영향 |
| Medium | 유지보수성, 성능, 확장성, 개발 속도에 영향          |
| Low    | 코드 가독성, 문서 품질, 작은 개선 사항            |

Ringdu에서는 다음 항목에 영향을 주면 `High`로 본다.

* 사용자 계정
* 비밀번호
* 인증 토큰
* 권한 검증
* 학원 소속 관계
* 학부모와 학생 연결 관계
* 출석 데이터
* 청구와 납부 데이터
* 운영 시크릿
* 배포 안정성

## 11. 기술부채 해결 절차

기술부채를 해결할 때는 다음 순서로 진행한다.

1. 기술부채 항목을 확인한다.
2. 현재도 유효한 문제인지 다시 확인한다.
3. 영향도와 우선순위를 재검토한다.
4. 관련 코드와 문서를 확인한다.
5. 필요한 경우 실행 계획을 작성한다.
6. 작은 단위로 수정한다.
7. 테스트 또는 수동 검증을 수행한다.
8. 관련 문서를 갱신한다.
9. 상태를 `Resolved`로 변경한다.
10. 해결 내용과 남은 문제를 기록한다.

기술부채 해결 중 새로운 문제가 발견되면 별도 항목으로 기록한다.

## 12. 기술부채 리뷰 체크리스트

정기적으로 다음을 확인한다.

* [ ] 오래된 기술부채가 방치되고 있지 않은가?
* [ ] P0 또는 P1 항목이 남아 있지 않은가?
* [ ] 보안 관련 기술부채가 해결되지 않은 상태로 남아 있지 않은가?
* [ ] 인증 또는 권한 검증 관련 문제가 남아 있지 않은가?
* [ ] 데이터 정합성에 영향을 주는 항목이 있는가?
* [ ] 프론트와 백엔드 API 계약이 불명확한 항목이 있는가?
* [ ] 배포 또는 운영 환경에 영향을 주는 항목이 있는가?
* [ ] 해결된 항목이 문서에 반영되었는가?
* [ ] 우선순위가 현재 상황에 맞게 조정되었는가?
* [ ] 더 이상 필요 없는 항목이 정리되었는가?

## 13. 기술부채와 실행 계획의 차이

기술부채와 실행 계획은 역할이 다르다.

| 구분    | 역할                    |
| ----- | --------------------- |
| 기술부채  | 현재 남아 있는 문제와 위험을 기록   |
| 실행 계획 | 어떤 순서로 작업하고 검증할지 정리   |
| 설계 문서 | 어떤 구조로 만들지와 선택 이유를 설명 |

예시:

```txt
docs/exec-plans/tech-debt-tracker.md
→ 테스트 부족, 문서 불일치, 임시 구현 등 남아 있는 문제 추적

docs/exec-plans/active/implement-auth.md
→ 인증 기능을 어떤 순서로 구현할지 정리

docs/design-docs/auth-design.md
→ 인증 구조와 토큰 흐름을 어떻게 설계할지 정리
```

기술부채 문서에는 브랜치명, 커밋 메시지, 세부 구현 순서를 과도하게 넣지 않는다.
그런 내용은 실행 계획 문서에서 관리한다.

## 14. Ringdu에서 특히 주의할 기술부채

Ringdu는 실제 운영을 고려하므로 다음 영역의 기술부채는 우선적으로 관리한다.

### 인증

주의할 항목:

* 비밀번호 암호화 누락
* JWT secret 하드코딩
* Access Token 장기 유효기간
* Refresh Token 원문 저장
* Refresh Token Redis key에 TTL 누락
* 인증 실패와 권한 실패 구분 부족
* 로그에 토큰 출력

---

### 권한

주의할 항목:

* 프론트에서 버튼만 숨기고 백엔드 검증이 없는 경우
* `ADMIN`, `OWNER`, `DESK` 일반 회원가입 차단 누락
* 학원 소속 검증 누락
* 학부모와 학생 연결 검증 누락
* 선생님이 담당하지 않는 학생 정보에 접근 가능한 경우

---

### 데이터베이스

주의할 항목:

* User에 학원 정보를 직접 넣는 구조
* 학원과 사용자 관계를 명확히 분리하지 않은 구조
* 학부모와 학생 관계가 불명확한 구조
* 상태값 관리가 불명확한 구조
* 삭제 정책이 불명확한 구조
* 인덱스가 필요한 조회에 인덱스가 없는 경우

---

### API

주의할 항목:

* Entity 직접 반환
* 요청 DTO와 응답 DTO 혼용
* 에러 응답 형식 불일치
* 프론트와 API 계약 불명확
* 민감정보가 응답에 포함되는 경우

---

### 테스트

주의할 항목:

* 인증 성공만 테스트하고 실패 케이스가 없는 경우
* 권한별 접근 테스트가 없는 경우
* 중복 이메일, 잘못된 권한, 잘못된 비밀번호 등 실패 케이스 누락
* 주요 서비스 로직 테스트 부족
* 프론트 연동에 필요한 API 응답 검증 부족

---

### 문서

주의할 항목:

* 문서와 실제 코드 구조 불일치
* 존재하지 않는 파일 경로를 안내하는 문서
* 이전 설계가 남아 있어 에이전트가 잘못된 기준으로 작업할 가능성
* 운영 기준과 개발 기준이 섞여 있는 문서

---

### 운영

주의할 항목:

* 운영 시크릿을 코드에 직접 작성
* 운영과 로컬 설정이 구분되지 않음
* Docker 볼륨 삭제 명령을 운영에서 사용할 위험
* 로그에서 장애 원인을 추적하기 어려운 구조
* 배포 후 롤백 기준이 없는 구조

---

## 15. 에이전트 작업 지침

AI 에이전트가 작업 중 기술부채를 발견하면 다음을 따른다.

* 즉시 수정 가능한 작은 문제는 수정한다.
* 범위가 큰 문제는 이 문서에 기록한다.
* 보안, 안정성, 데이터 정합성과 관련된 문제는 우선순위를 높게 둔다.
* 임시 구현을 추가했다면 반드시 기술부채로 남긴다.
* 기술부채를 기록할 때는 문제, 영향, 해결 방향을 함께 작성한다.
* 해결한 기술부채는 상태를 `Resolved`로 변경하고 해결 내용을 남긴다.
* 기술부채를 숨기지 않는다.
* 문서와 코드가 다르면 현재 정상 동작하는 코드를 기준으로 판단한다.
* 기술부채 해결을 이유로 불필요한 대규모 리팩토링을 진행하지 않는다.
* 기능 구현 중 발견한 큰 구조 문제는 별도 이슈나 실행 계획으로 분리한다.

## 17. 핵심 원칙 요약

* 기술부채는 실패가 아니라 관리 대상이다.
* 기록하지 않은 기술부채는 반복해서 문제를 만든다.
* 모든 미구현 기능을 기술부채로 보지 않는다.
* 임시 구현, 보안 위험, 테스트 부족, 문서 불일치는 기술부채로 기록한다.
* 보안, 안정성, 데이터 정합성 문제는 우선적으로 해결한다.
* 당장 해결하지 못해도 문제와 영향을 명확히 남긴다.
* 해결 완료 여부는 검증 기준으로 판단한다.
* 완료된 항목도 삭제하지 않고 이력으로 보관한다.

```

이 버전은 예시 기술부채를 억지로 박아두지 않고, **Ringdu 프로젝트에서 기술부채를 판단하고 기록하는 공통 기준**으로 정리한 거야.
```
