# 실행 계획: 학부모·학생 청구 조회와 수납 기준일 확장

## 1. 목표

수납 기준일을 31일까지 지원하고 존재하지 않는 날짜는 월말로 보정한다. 학부모는 활성 연결 자녀의 청구를, 학생은 본인 청구를 조회 전용 화면에서 확인할 수 있게 한다.

## 2. 배경

기존 청구 관리는 학원 역할에 한정되어 있고 수납 기준일이 28일까지 제한되어 있다. 실제 학원 운영의 말일 청구와 학부모·학생의 수납 현황 확인 요구를 지원해야 한다.

## 3. 작업 범위

포함되는 작업:

- 수납 기준일 1~31 검증과 월말 보정
- 학부모 활성 자녀 관계 기반 청구 조회 API
- 학생 본인 프로필 기반 청구 조회 API
- 학부모·학생 청구 조회 전용 페이지와 홈 진입 카드
- 백엔드 통합 테스트, 프론트 lint/build 검증

포함하지 않는 작업:

- PG 및 카드·계좌 결제
- 학부모·학생의 청구 수정, 수납, 취소
- 학원 사이드바 청구 메뉴
- 출석·상담 기능 변경

## 6. 구현 순서

1. 수납 기준일과 월말 계산 정책을 변경한다.
2. 조회 전용 응답 DTO, 권한 서비스, 컨트롤러를 추가한다.
3. 학부모·학생 권한 및 날짜 보정 통합 테스트를 추가한다.
4. 프론트 API와 조회 전용 화면을 구현한다.
5. 전체 검증 후 기존 PR 브랜치에 커밋한다.

## 7. 검증 방법

- `./gradlew test`
- `npm run lint`
- `npm run build`
- 학부모 활성 관계 및 비연결 접근 통합 테스트
- 학생 본인 프로필 범위 통합 테스트
- 2월·4월의 31일 월말 보정 테스트

## 8. 위험 요소

- 학생 계정은 여러 학원 프로필을 가질 수 있으므로 학생 조회는 본인 `userId`의 모든 활성 프로필을 포함해야 한다.
- 학부모 관계는 사용자 간 관계이므로 요청된 학생 프로필의 `userId`와 활성 관계를 함께 검증해야 한다.
- 기준일 31일은 생성 가능 시점도 월말로 보정하지 않으면 2월에 자동 생성할 수 없다.

## 9. 롤백 방법

조회 전용 컨트롤러와 프론트 라우트를 제거하면 기존 학원 관리 기능은 유지된다. 기준일 검증과 계산은 이전 28일 정책으로 독립적으로 복구할 수 있다.
