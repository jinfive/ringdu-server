# 실행 계획: 유연한 학생 청구/수납 관리

## 1. 목표

학생 상세 화면은 이번 달 청구 요약만 표시하고, 수납 설정과 청구 생성, 청구 내역, 수납 처리는 반응형 관리 모달에서 제공한다. 정규 월 청구 자동 생성은 유지하면서 3개월 선납과 보강비, 교재비 같은 임의 청구를 하나의 청구서로 생성할 수 있게 한다.

## 2. 배경

기존 화면은 학생 상세 탭에 모든 관리 기능을 펼쳐 좁은 화면에서 길어지고, 기존 데이터 모델은 학생별 월 청구를 하나만 허용해 실제 학원에서 발생하는 추가 비용과 선납 청구를 표현할 수 없다.

## 3. 작업 범위

포함되는 작업:

- 청구 유형 및 청구 기간 필드 추가
- 정규 자동 청구 중복 방지 정책 유지
- 임의 청구 생성 API와 검증 추가
- 청구 응답, 목록, 수정, 수납, 취소 흐름 보완
- 학생 상세 청구 탭 요약화 및 관리 모달 구현
- 백엔드 통합 테스트와 프론트 lint/build 검증
- 제품 스펙과 생성 DB 스키마 문서 갱신

포함하지 않는 작업:

- PG 결제 연동
- 학부모 청구 조회
- 별도 청구/수납 사이드바 메뉴
- 출석 및 상담 기능 변경

## 6. 구현 순서

1. 청구 모델과 저장소 조회 정책을 확장한다.
2. 임의 청구 생성 API와 검증 및 테스트를 추가한다.
3. 프론트 타입과 API 함수를 새 계약에 맞춘다.
4. 학생 상세 요약과 관리 모달 UI를 구현한다.
5. 전체 테스트를 실행하고 문서를 완료 상태로 이동한다.

## 7. 검증 방법

- `./gradlew test`
- `npm run lint`
- `npm run build`
- 정규 청구 중복 생성 방지 통합 테스트
- 같은 기간의 수동 청구 복수 생성 통합 테스트
- 기간 역전, 타 학원 학생 접근, 수납/수정/취소 정책 통합 테스트

## 8. 위험 요소

- 기존 월 유니크 제약 제거 시 자동 청구 중복이 생기지 않도록 서비스 조회 조건이 정확해야 한다.
- `ddl-auto=update` 환경에서는 기존 유니크 제약 제거가 자동 반영되지 않을 수 있어 운영 DB 적용 시 별도 DDL 확인이 필요하다.
- 대표 청구월과 기간 필드가 혼재하므로 기존 응답 호환성을 유지해야 한다.

## 9. 롤백 방법

추가 필드는 nullable 호환 형태로 유지하고 기존 API 필드를 보존한다. 문제가 발생하면 수동 생성 엔드포인트와 프론트 노출을 되돌리고 정규 월 청구 흐름만 사용할 수 있다.
