# 실행 계획: 학생 청구/수납 API 연결

## 1. 목표

학생 관리 안에서 학생별 수납 설정, 월 청구서 생성, 금액 수정, 수납 처리, 취소를 관리하고 프론트엔드의 로컬 상태 구현을 실제 API로 교체한다.

## 2. 작업 범위

포함:

- 학생별 월 수강료와 수납 기준일 저장
- 현재 월 청구서 보장 API
- 월별 청구 내역과 요약 조회
- 청구 금액 수정, 누적 수납, 취소
- 학원 소유권 검증과 상태 전이 테스트
- 좁은 학생 상세 패널에 맞춘 청구 UI 및 API 연결

제외:

- PG, 카드, 계좌 결제 연동
- 학부모 청구 조회
- 백그라운드 자동 청구 배치
- 별도 청구/수납 사이드바 메뉴

## 3. 관련 문서

## 4. 구현 순서

1. 청구 설정, 청구서, 수납 이력 엔티티와 저장소를 추가한다.
2. 학원 소유권과 상태 전이를 검증하는 서비스와 API를 추가한다.
3. API 통합 테스트로 생성, 수정, 수납, 취소 규칙을 검증한다.
4. 프론트 로컬 상태를 제거하고 API 호출과 반응형 UI를 연결한다.
5. 전체 테스트와 브라우저 레이아웃을 확인한다.

## 5. 위험 요소

- 화면 진입 시 `ensure-current`가 반복 호출되지 않도록 학생/탭 단위로 한 번만 실행해야 한다.
- 청구 금액을 이미 수납한 금액보다 낮게 변경하면 데이터 일관성이 깨지므로 차단해야 한다.
- 월별 청구서 중복 생성은 DB 유일 제약과 서비스 조회를 함께 사용해 방어한다.

## 6. 롤백 방법

청구 도메인 패키지와 프론트 청구 API 연결 커밋을 되돌린다. 기존 학생, 상담, 출석 테이블과 API는 수정하지 않는다.

## 7. 완료 기준

- [x] 학원은 자기 학생의 수납 설정과 청구서만 관리할 수 있다.
- [x] 기준일 도래 후 현재 월 청구서가 한 번만 생성된다.
- [x] 부분수납, 완납, 취소 상태 전이가 검증된다.
- [x] 프론트가 localStorage 없이 API 데이터를 표시한다.
- [x] 좁은 상세 패널과 모바일에서 청구 카드가 겹치지 않는다.
- [x] 백엔드 테스트, 프론트 lint/build가 통과한다.
