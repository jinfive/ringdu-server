# Reliability

## 1. 목적

이 문서는 Ringdu 프로젝트의 안정성 기준을 정의한다.

Ringdu는 학원, 선생님, 학부모, 학생을 연결하는 학원 관리 웹/앱 서비스이며, 실제 배포와 운영까지 고려한다.  
서비스는 정상 상황뿐 아니라 장애, 지연, 외부 서비스 실패, 데이터 오류, 배포 문제와 같은 비정상 상황에서도 가능한 한 안전하게 동작해야 한다.

이 문서는 다음 내용을 다룬다.

- 안정성 목표
- 운영상 위험 요소
- 주요 실패 방식
- 장애 예방 원칙
- 데이터 정합성 기준
- 인증과 권한 안정성
- 장애 감지와 모니터링
- 복구 계획
- 배포와 롤백 기준
- 에이전트 작업 지침

---

## 2. 안정성 목표

Ringdu는 다음 안정성 목표를 따른다.

- 핵심 기능은 예측 가능하게 동작해야 한다.
- 장애가 발생해도 피해 범위를 최소화해야 한다.
- 실패 원인을 추적할 수 있어야 한다.
- 중요한 작업은 중복 실행이나 데이터 손상을 피해야 한다.
- 인증과 권한 검증은 안정적으로 동작해야 한다.
- 학원, 학생, 학부모 관계 데이터는 정합성을 유지해야 한다.
- 외부 서비스가 실패해도 전체 시스템이 불필요하게 중단되지 않아야 한다.
- 배포 후 문제가 발생하면 빠르게 롤백하거나 복구할 수 있어야 한다.
- 에러는 숨기지 않고 관찰 가능해야 한다.

Ringdu에서는 특히 다음 영역의 안정성을 중요하게 본다.

```txt
회원가입
로그인
토큰 재발급
권한 검증
학원 소속 관계
학부모-학생 연결
출석 관리
숙제 관리
청구와 납부
운영자 기능
```

## 3. 운영상 위험 요소

다음과 같은 운영상 위험을 고려한다.

- 데이터베이스 장애
- Redis 장애
- 네트워크 지연 또는 끊김
- 외부 API 실패
- OAuth 제공자 장애
- 파일 저장소 장애
- 알림 발송 실패
- 배포 실패
- 잘못된 환경 변수 설정
- JWT secret 설정 오류
- DB 마이그레이션 오류
- 스키마 변경 오류
- 트래픽 급증
- 메모리 부족
- 디스크 부족
- 권한 설정 오류
- 로그 또는 모니터링 누락
- 데이터 정합성 오류
- 다른 학원 데이터 접근 가능성
- 학부모가 연결되지 않은 학생 정보를 조회하는 문제

---

## 4. 주요 실패 방식

서비스는 다음과 같은 방식으로 실패할 수 있다.

### 요청 실패

- API 요청이 시간 초과될 수 있다.
- 잘못된 입력으로 요청이 실패할 수 있다.
- 인증 또는 권한 문제로 요청이 거부될 수 있다.
- 외부 서비스 응답 지연으로 요청이 실패할 수 있다.
- 프론트엔드와 백엔드 API 계약 불일치로 요청이 실패할 수 있다.

---

### 데이터 실패

- 데이터 저장이 실패할 수 있다.
- 중복 데이터가 생성될 수 있다.
- 일부 데이터만 저장되고 나머지가 실패할 수 있다.
- 잘못된 트랜잭션 처리로 데이터 정합성이 깨질 수 있다.
- 학원과 사용자 관계가 잘못 연결될 수 있다.
- 학부모와 학생 관계가 중복되거나 누락될 수 있다.
- 출석, 숙제, 청구 상태가 잘못 변경될 수 있다.

---

### 인증 실패

- Access Token이 만료될 수 있다.
- Refresh Token이 만료되거나 폐기될 수 있다.
- Redis 장애로 Refresh Token 검증이 실패할 수 있다.
- Refresh Token 재사용 공격이 감지될 수 있다.
- JWT secret 설정 오류로 토큰 검증이 실패할 수 있다.
- 쿠키 설정 오류로 Refresh Token이 전달되지 않을 수 있다.

---

### 권한 실패

- 권한이 없는 사용자가 API에 접근할 수 있다.
- 프론트에서 숨긴 기능을 직접 API 호출로 실행할 수 있다.
- 선생님이 담당하지 않는 학생 정보에 접근할 수 있다.
- 학부모가 연결되지 않은 학생 정보에 접근할 수 있다.
- 다른 학원의 학생, 출석, 청구 정보를 조회할 수 있다.
- OWNER, DESK, TEACHER의 학원 내 권한 범위가 혼동될 수 있다.

---

### 외부 연동 실패

- 외부 API가 응답하지 않을 수 있다.
- 외부 API 응답 형식이 바뀔 수 있다.
- 외부 서비스의 인증 정보가 만료될 수 있다.
- Webhook이 중복 전달되거나 누락될 수 있다.
- 이메일, 문자, 푸시 알림이 실패할 수 있다.
- 파일 저장소 업로드 또는 다운로드가 실패할 수 있다.

---

### 배포 실패

- 새 버전에서 기존 기능이 깨질 수 있다.
- 환경 변수 누락으로 애플리케이션이 실행되지 않을 수 있다.
- DB 마이그레이션이 실패할 수 있다.
- 롤백이 어려운 변경이 배포될 수 있다.
- 운영 Redis, PostgreSQL 연결 설정이 잘못될 수 있다.
- CORS 또는 Cookie 설정 오류로 인증 흐름이 깨질 수 있다.

---

## 5. 안정성 원칙

기본 안정성 원칙은 다음과 같다.

- 실패 가능성을 전제로 설계한다.
- 중요한 작업은 트랜잭션 경계를 명확히 한다.
- 외부 서비스 호출에는 타임아웃을 설정한다.
- 재시도는 신중하게 적용한다.
- 중복 요청에 안전한 구조를 고려한다.
- 장애가 발생해도 전체 시스템으로 전파되지 않도록 한다.
- 에러는 기록하고 추적 가능하게 만든다.
- 사용자가 이해할 수 있는 에러 응답을 제공한다.
- 복구하기 어려운 변경은 작게 나누어 진행한다.
- 배포 전 검증 방법을 명확히 한다.
- 운영 시크릿은 코드에 직접 작성하지 않는다.
- 권한 검증은 프론트가 아니라 백엔드에서 수행한다.

---

## 6. 트랜잭션과 데이터 정합성

데이터 변경 작업은 정합성을 유지해야 한다.

원칙:

- 하나의 비즈니스 작업은 필요한 범위 안에서 트랜잭션으로 묶는다.
- 여러 데이터를 함께 변경할 때 일부만 성공하지 않도록 주의한다.
- 읽기 작업과 쓰기 작업의 트랜잭션 설정을 구분한다.
- 중복 생성이 문제가 되는 데이터에는 고유 제약조건을 고려한다.
- 상태 변경은 가능한 한 명확한 상태값으로 관리한다.
- 삭제가 위험한 데이터는 soft delete 또는 상태 변경을 고려한다.
- 데이터 변경 실패 시 어떤 상태로 남는지 확인한다.
- 상태 변경 이력이 필요한 기능은 로그 또는 이력 테이블을 고려한다.

검토 대상:

```txt
회원가입
로그인
토큰 재발급
학원 생성
학원 구성원 등록
선생님 승인
학생 등록
학부모-학생 연결
출석 체크
숙제 등록과 제출
청구서 발행
납부 상태 변경
파일 업로드
알림 발송
권한 변경
```

---

## 7. 인증 안정성

인증 흐름은 서비스 안정성의 핵심이다.

원칙:

- Access Token과 Refresh Token의 역할을 구분한다.
- Access Token은 짧은 수명으로 관리한다.
- Refresh Token은 HttpOnly Cookie로 관리한다.
- Refresh Token 원문은 저장하지 않는다.
- Redis에는 Refresh Token 해시값만 저장한다.
- Refresh Token Rotation을 적용한다.
- 재사용이 감지된 Refresh Token은 세션 폐기 대상으로 본다.
- 로그아웃 시 Refresh Token 상태를 폐기한다.
- Redis 장애 시 사용자에게 안전한 실패 응답을 제공한다.
- JWT secret은 환경변수로 관리한다.
- 운영 환경에서는 Cookie `Secure=true`를 적용한다.

주의:

- Access Token은 DB에 저장하지 않는다.
- Refresh Token 원문은 DB나 Redis에 저장하지 않는다.
- 토큰 값은 로그에 남기지 않는다.
- 인증 실패와 권한 실패를 구분한다.

---

## 8. 권한 안정성

Ringdu는 여러 사용자 역할이 함께 사용하는 서비스이므로 권한 안정성이 중요하다.

권한:

```txt
ADMIN
OWNER
DESK
TEACHER
PARENT
STUDENT
```

원칙:

- 권한 검증은 반드시 백엔드에서 수행한다.
- 프론트에서 버튼을 숨기는 것은 보안이 아니다.
- `ADMIN`, `OWNER`, `DESK`는 일반 회원가입으로 생성하지 않는다.
- OWNER는 자신이 관리하는 학원의 데이터만 관리해야 한다.
- DESK는 소속 학원의 운영 데이터만 접근해야 한다.
- TEACHER는 담당 범위의 수업, 학생, 숙제, 출석 정보만 접근해야 한다.
- PARENT는 연결된 자녀의 정보만 조회해야 한다.
- STUDENT는 본인 정보만 조회하거나 제출해야 한다.
- 다른 학원의 데이터에 접근할 수 없어야 한다.

권한 검증이 필요한 대표 기능:

```txt
학원 정보 조회/수정
학원 구성원 관리
학생 등록/수정
학부모-학생 연결
출석 등록/수정
숙제 등록/검토
청구서 발행
납부 상태 변경
관리자 기능
```

---

## 9. 외부 서비스 호출

외부 서비스는 항상 실패할 수 있다고 가정한다.

원칙:

- 외부 API 호출에는 타임아웃을 설정한다.
- 응답 실패 시 사용자에게 적절한 메시지를 제공한다.
- 무한 재시도를 하지 않는다.
- 재시도는 멱등성이 보장되는 경우에만 신중하게 적용한다.
- 외부 API 응답을 그대로 신뢰하지 않는다.
- 외부 서비스 장애가 내부 시스템 전체 장애로 이어지지 않도록 한다.
- 외부 연동 실패 기록을 남긴다.
- 외부 서비스 인증 정보는 환경변수로 관리한다.

외부 서비스 예시:

```txt
카카오 OAuth
네이버 OAuth
구글 OAuth
이메일 발송
SMS 발송
푸시 알림
파일 저장소
결제 서비스
분석 도구
```

현재 실제 OAuth 연동 전이라면, 간편가입 버튼은 준비 중 상태로 처리하고 실제 인증 흐름에 포함하지 않는다.

---

## 10. 재시도와 멱등성

재시도는 장애 대응에 도움이 될 수 있지만, 잘못 사용하면 중복 처리 문제를 만든다.

원칙:

- 재시도 가능한 작업과 불가능한 작업을 구분한다.
- 결제, 청구, 납부 상태 변경처럼 중복 실행이 위험한 작업은 멱등성을 고려한다.
- 출석 체크처럼 중복 요청이 생길 수 있는 기능도 중복 처리 기준을 정한다.
- 클라이언트 재요청으로 같은 작업이 여러 번 처리되지 않게 한다.
- 필요한 경우 요청 ID 또는 idempotency key를 사용한다.
- 재시도 횟수와 간격을 제한한다.
- 실패한 작업은 추적 가능해야 한다.

중복 처리에 주의할 기능:

```txt
회원가입
학원 구성원 초대
학생 등록
학부모-학생 연결 요청
출석 체크
숙제 제출
청구서 발행
납부 처리
알림 발송
파일 업로드
```

---

## 11. 에러 처리

에러는 일관되고 추적 가능하게 처리한다.

원칙:

- 에러 응답 형식을 통일한다.
- 사용자에게 내부 구현 정보를 노출하지 않는다.
- 시스템 에러와 비즈니스 에러를 구분한다.
- 인증 실패와 권한 실패를 구분한다.
- 에러 발생 시 원인을 추적할 수 있는 로그를 남긴다.
- 같은 에러가 반복되면 알림 또는 모니터링 대상이 되어야 한다.
- 예외를 무시하거나 빈 catch 블록으로 처리하지 않는다.
- 민감정보를 에러 메시지에 포함하지 않는다.

좋지 않은 예:

```txt
try {
  ...
} catch (Exception e) {
}
```

좋은 방향:

```txt
- 실패 원인을 기록한다.
- 필요한 경우 사용자에게 안전한 에러 메시지를 반환한다.
- 복구 가능한 실패와 복구 불가능한 실패를 구분한다.
- ErrorCode 기반으로 일관된 응답을 반환한다.
```

---

## 12. 로그

로그는 장애 분석과 복구에 필요하다.

로그 원칙:

- 중요한 상태 변경은 로그로 추적 가능해야 한다.
- 장애 원인을 찾을 수 있는 최소한의 정보를 남긴다.
- 민감정보는 로그에 남기지 않는다.
- 반복적인 불필요한 로그는 줄인다.
- 에러 로그에는 원인, 위치, 요청 흐름을 파악할 수 있는 정보가 있어야 한다.
- 사용자 식별자는 필요한 경우 최소한으로 남긴다.
- 운영 로그는 장애 대응에 도움이 되는 수준으로 남긴다.

기록하면 좋은 이벤트:

```txt
회원가입 실패
로그인 실패
토큰 재발급 실패
Refresh Token 재사용 감지
권한 거부
학원 구성원 등록/변경
학생 등록/변경
학부모-학생 연결/해제
출석 변경
숙제 등록/제출
청구서 발행/상태 변경
외부 API 호출 실패
파일 업로드 실패
관리자 작업
배포 후 주요 오류
```

로그에 포함하면 안 되는 정보:

```txt
비밀번호
Access Token
Refresh Token
API Key
개인키
전체 개인정보
민감한 요청 본문
```

## 16. 데이터베이스 안정성

데이터베이스는 서비스 안정성의 핵심이다.

원칙:

- 불필요하게 무거운 쿼리를 피한다.
- 목록 조회에는 페이지네이션을 적용한다.
- 자주 조회하는 조건에는 인덱스를 검토한다.
- 트랜잭션 범위를 과도하게 넓히지 않는다.
- N+1 문제를 주의한다.
- 대량 데이터 변경은 작은 단위로 나누어 처리한다.
- 마이그레이션 전후 데이터 정합성을 확인한다.
- 운영 DB 작업은 신중하게 진행한다.
- 외래키와 unique 제약조건을 적절히 사용한다.

Ringdu에서 특히 주의할 DB 관계:

```txt
users
academies
academy_members
students
student_guardians
academy_students
attendance_records
homework_assignments
homework_submissions
billing_invoices
payment_records
```

주의:

- User에 학원 정보를 직접 넣지 않는다.
- 학원과 사용자 관계는 AcademyMember로 관리한다.
- 학부모와 학생 관계는 StudentGuardian으로 관리한다.
- 학원과 학생 관계는 AcademyStudent로 관리한다.
- Refresh Token 원문은 DB에 저장하지 않는다.

## 17. Redis와 캐시 안정성

Redis는 Refresh Token 상태 저장소로 사용할 수 있다.

원칙:

- Redis는 원본 데이터 저장소가 아니다.
- Redis 장애 시 인증 흐름이 어떻게 실패할지 정의한다.
- Refresh Token 원문은 Redis에 저장하지 않는다.
- tokenHash만 저장한다.
- TTL을 명확히 설정한다.
- 만료된 토큰 상태가 오래 남지 않도록 한다.
- Refresh Token Rotation과 재사용 감지 흐름을 명확히 한다.
- Redis key 구조를 문서화한다.

예상 key 구조:

```txt
refresh:{tokenHash}
used-refresh:{oldTokenHash}
```

주의:

- Access Token은 Redis에 저장하지 않는다.
- Refresh Token 원문을 로그에 남기지 않는다.
- Redis 장애를 무시하고 인증을 통과시키면 안 된다.

## 18. 배치와 비동기 작업

배치와 비동기 작업은 실패 추적이 가능해야 한다.

원칙:

- 작업 시작과 종료를 기록한다.
- 실패한 작업을 추적할 수 있어야 한다.
- 중복 실행 시 문제가 없는지 확인한다.
- 재시도 기준을 정한다.
- 오래 걸리는 작업은 진행 상태를 확인할 수 있어야 한다.
- 작업 실패가 사용자 데이터 정합성을 깨지 않도록 한다.

Ringdu에서 배치 또는 비동기 작업이 될 수 있는 예시:

```txt

만료 토큰 정리
청구서 발행 예약
납부 상태 동기화
출석 알림 발송
숙제 마감 알림 발송
파일 정리
```

## 19. 성능과 용량

성능 문제는 안정성 문제로 이어질 수 있다.

원칙:

- 응답 시간이 긴 API는 원인을 분석한다.
- 대량 조회 API에는 페이지네이션을 적용한다.
- 필요 없는 데이터를 과하게 조회하지 않는다.
- 파일, 이미지, 대용량 데이터 처리는 별도 전략을 고려한다.
- 트래픽 증가에 따른 병목 지점을 파악한다.
- 리소스 사용량을 모니터링한다.
- 자주 조회되는 목록은 조회 조건과 인덱스를 함께 검토한다.

성능 검토가 필요한 화면:

```txt
학생 목록
출석 목록
숙제 목록
청구서 목록
납부 내역
알림 목록
관리자 로그
```

## 20. 장애 대응 절차

장애가 발생하면 다음 순서로 대응한다.

1. 장애 범위를 파악한다.
2. 영향을 받는 기능과 사용자를 확인한다.
3. 최근 배포나 설정 변경이 있었는지 확인한다.
4. 로그와 모니터링 지표를 확인한다.
5. 임시 완화 조치를 적용한다.
6. 필요하면 롤백한다.
7. 근본 원인을 분석한다.
8. 재발 방지 작업을 기록한다.
9. 관련 문서와 테스트를 갱신한다.

장애 대응 후에는 다음을 남긴다.

- 발생 시간
- 영향 범위
- 원인
- 임시 조치
- 최종 조치
- 재발 방지 작업
- 추가 기술부채 여부

장애 복구는 영향도가 큰 기능부터 진행한다.

일반적인 우선순위:

1. 인증과 로그인

3. 학원과 사용자 소속 관계

8. 관리자 편의 기능

다만 보안, 데이터 정합성, 사용자 접근 제어 문제는 항상 높은 우선순위로 본다.

## 23. 에이전트 작업 지침

AI 에이전트가 안정성과 관련된 코드를 수정할 때는 다음을 따른다.

- 이 문서를 먼저 확인한다.
- 장애 가능성을 고려한다.

## 25. 핵심 원칙 요약

- 안정성은 장애가 없을 때가 아니라 장애가 났을 때 드러난다.
- 실패 가능성을 전제로 설계한다.
- 인증, 권한, 데이터 정합성 문제는 높은 우선순위로 본다.
- User에 학원 정보를 직접 넣지 않는다.
- 학원, 학생, 학부모 관계는 별도 테이블로 분리한다.
- Refresh Token 원문은 저장하지 않는다.
- 중요한 상태 변경은 트랜잭션과 검증 기준을 명확히 한다.
- 에러는 숨기지 않고 추적 가능하게 만든다.
- 민감정보는 로그에 남기지 않는다.
- 배포 전후 검증과 롤백 방법을 고려한다.
- 임시 해결은 기술부채로 기록한다.
