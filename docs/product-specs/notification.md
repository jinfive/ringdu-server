# Notification Inbox

## 1. 목적

알림함은 Ringdu의 주요 역할 사용자가 자기에게 필요한 업무 이벤트를 한곳에서 확인하는 공통 진입점이다.

초기에는 학원-선생님 초대장처럼 사용자가 직접 처리해야 하는 이벤트를 놓치지 않게 하는 데 집중한다. 이후 출석, 청구서/수납, 상담 일정, 공지처럼 역할별 업무 흐름과 연결되는 알림으로 확장한다.

## 2. 적용 대상 role

공통 알림함은 다음 역할을 대상으로 한다.

```txt
ACADEMY
TEACHER
PARENT
STUDENT
```

`ADMIN` 운영 알림은 일반 사용자 알림함과 요구사항이 다르므로 별도 운영 화면에서 다루는 방향으로 검토한다.

## 3. 알림 유형 예시

MVP 이후 확장 가능한 알림 예시는 다음과 같다.

- 선생님 초대장 수신
- 학원 초대 수락/거절 결과
- 출석 관련 알림
- 청구서/수납 알림
- 상담 일정 알림
- 공지 알림

## 4. 기본 상태

알림의 기본 읽음 상태는 다음 두 가지로 시작한다.

```txt
UNREAD
READ
```

알림 생성 시 기본값은 `UNREAD`다. 사용자가 알림 상세를 확인하거나 읽음 처리 API를 호출하면 `READ`로 변경한다.

## 5. 확장 상태 또는 타입

알림 타입은 도메인 확장을 고려해 다음 값부터 시작한다.

```txt
INVITATION
ATTENDANCE
INVOICE
CONSULTATION
NOTICE
```

각 타입은 연결 대상 리소스를 가질 수 있다. 예를 들어 `INVITATION`은 초대장 ID, `INVOICE`는 청구서 ID, `NOTICE`는 공지 ID를 참조할 수 있다.

## 6. MVP 구현 방향

처음에는 초대장 알림부터 시작한다.

MVP 범위:

- TEACHER가 학원 초대장을 받으면 알림함에 `INVITATION` 알림을 표시한다.
- ACADEMY는 선생님이 초대장을 수락 또는 거절한 결과를 알림으로 확인할 수 있다.
- 알림 목록은 최신순으로 제공한다.
- 알림 상태는 `UNREAD`, `READ`만 사용한다.

MVP에서 제외:

- 실제 문자, 이메일, 푸시 발송
- 알림 예약 발송
- 사용자별 알림 채널 설정
- 대량 알림 발송 관리

이후 출석, 청구서, 상담, 공지 도메인이 구현되면 같은 알림함 모델에 타입을 추가해 확장한다.

## 7. 후속 API 후보

후속 구현 시 검토할 API는 다음과 같다.

```txt
GET /api/notifications
PATCH /api/notifications/{id}/read
PATCH /api/notifications/read-all
```

권한 기준:

- 로그인한 사용자만 자기 알림을 조회할 수 있다.
- 다른 사용자의 알림 ID로 읽음 처리할 수 없어야 한다.
- 알림의 연결 리소스도 해당 사용자가 접근 가능한 범위여야 한다.
